# Bagualu 代理池服务 SDD

状态：Draft

## 1. 文档说明

本文档用于指导 AI 大模型或开发人员实现 Bagualu 代理池项目。本文档只定义产品需求、系统边界、模块架构、页面、接口和验收标准；技术实现路线已确定（见 1.1），变更技术路线必须先更新本文档并评审。

在需求确认完成前，只维护本文档，不开始编写业务代码。

### 1.1 技术实现路线（已确定）

技术实现在此基础上执行；数据库 ORM 与其余第三方库在满足本节约束的前提下，由实现阶段选择。

- 后端主服务使用 Go 编写，编译为静态二进制（`CGO_ENABLED=0`），按 OpenWrt 目标架构交叉编译，以 ipk 形式安装运行（见第 5 节）。
- Mihomo 仅作为 Bagualu 的运行时内核依赖包提供代理协议能力；Bagualu 主程序负责全部业务能力，并管理 Mihomo 子进程，通过 Mihomo HTTP 控制 API 和本地代理端口使用内核能力（见 4.3、4.4）。Bagualu 安装包必须声明与目标架构匹配的 Mihomo 依赖，第一版不复用、不接管系统或其他插件提供的 Mihomo 二进制，也不直接调用 Mihomo `core` 包或其他底层 Go 包。
- 数据存储默认使用 SQLite，采用纯 Go 驱动（`modernc.org/sqlite`），不依赖 cgo，单文件持久化于数据目录；测试结果写入需控制频率与总量，避免闪存和内存压力。
- 独立管理后台使用 React + TypeScript + Vite + Ant Design 构建为静态单页应用，由 Go 服务通过 `embed.FS` 托管；OpenWrt 设备运行时不依赖 Node.js，静态资源本地化，不依赖公网 CDN。
- LuCI 设置页保持 OpenWrt 原生轻量实现，不引入前端框架；复杂功能由独立管理后台承担。
- 包管理采用官方 OpenWrt SDK 构建 ipk：按目标架构出包，Bagualu 主程序、Mihomo 运行时依赖包与 LuCI 文件可以分别打包，但 Bagualu 包必须依赖匹配版本的 Mihomo 包，且只有 Bagualu 主程序注册并运行 OpenWrt 服务；配置与数据分离，升级保留用户配置。

## 2. 项目目标

Bagualu 是一个运行在 OpenWrt 路由器上的代理池管理服务，主要能力是：

1. 收集多个代理订阅作为上游。
2. 解析订阅中的代理节点并统一管理。
3. 通过分组组织节点资源。
4. 对节点进行真实的连通性、延迟和下载速度测试。
5. 通过可视化页面查看上游、节点、分组和测试结果。
6. 通过 API Key 获取指定分组的代理订阅资源。

系统不做代理转发。系统自身只负责订阅收集、节点管理、节点测试、结果展示和资源输出。

## 3. 角色

### 3.1 管理员

管理员通过 Web 页面管理系统，可以：

- 管理订阅上游。
- 查看和管理节点。
- 创建和维护分组。
- 配置节点测试策略。
- 查看节点连通性、延迟和下载速度。
- 管理 API Key。
- 查看任务执行记录和系统状态。

### 3.2 API 使用者

API 使用者不需要进入管理页面，通过 API Key 获取被授权分组的订阅资源。

### 4.1 模块说明

| 模块 | 作用 |
| --- | --- |
| Web 管理页面 | 提供系统配置、节点管理、分组管理、测试结果和任务状态的可视化操作。 |
| HTTP API 服务 | 为页面、外部客户端和 OpenWrt 服务提供统一接口。 |
| 定时任务服务 | 按计划执行订阅刷新、节点测试和历史数据清理。 |
| Bagualu 内核适配层 | Bagualu 内部生成 Mihomo 配置，通过 Mihomo HTTP 控制 API 管理节点和逻辑测试连接，通过本地代理端口发起测试，并读取 HTTP API 暴露的连接与流量数据。 |
| Mihomo 内核依赖包 | Bagualu 随包安装的代理协议内核，只负责实际协议连接、握手、代理转发和原始流量数据；不承担 Bagualu 业务逻辑。 |
| 数据存储 | 保存上游、节点、分组、测试结果、任务和 API Key。 |
| OpenWrt 服务封装 | 负责开机启动、停止、重启、配置加载和日志输出。 |

### 4.2 运行形态

第一版只支持一种运行形态：Web 页面、HTTP API、定时任务、数据存储、业务逻辑、任务调度和 Mihomo 依赖管理全部由 Bagualu 主程序负责；Mihomo 仅以一个由 Bagualu 管理的内核依赖进程提供内核能力，所有测试任务共享该进程并使用相互隔离的逻辑连接。Mihomo 不是独立 OpenWrt 服务，不注册独立 LuCI 菜单、独立 init 服务或独立业务 API。

### 4.3 Bagualu 与 Mihomo 内核依赖联动

Mihomo 是节点测试和真实测速所需的运行时内核依赖包。Bagualu 主程序负责所有业务流程，不直接实现代理协议，也不链接 Mihomo 源码或 `core` 包；Bagualu 只通过内部 HTTP 适配层调用 Mihomo 的 HTTP 控制 API，并通过本地代理端口承载测试流量。

联动关系如下：

```text
节点配置 + 测试参数
        |
        v
Bagualu 任务服务
        |
        v
Bagualu 内核适配层
        |
        +--> 生成并维护 Bagualu 专用 Mihomo 配置
        +--> 启动或复用 Bagualu 管理的 Mihomo 进程
        +--> 通过 HTTP API 加载配置、选择节点和读取状态
        +--> 获取本地代理入口
        +--> 发起测试请求
        +--> 读取连接状态、字节数和耗时
        +--> 释放本次测试的连接和任务状态，不停止共享进程
        |
        v
Mihomo 内核依赖包
        |
        v
节点真实出口
```

第一版不额外开发独立的内核业务服务。Mihomo 仅作为 Bagualu 的运行时内核依赖包，以 Bagualu 管理的子进程运行；Bagualu 主程序负责其配置、启动、停止、重启和控制 API 调用，边界如下：

- **进程启动与监督**：LuCI 通过 ubus/procd 只启动、停止、重启和监督 Bagualu 主程序；Bagualu 主程序负责创建、停止、监控和按退避策略重启自己启动的 Mihomo 子进程。
- **配置准备**：Bagualu 生成或更新自身独立目录中的 Mihomo 配置，并在启动或配置变更时通过自身控制流程使配置生效，不触碰 OpenClash 文件。
- **控制 API 调用**：Bagualu 使用 Go 标准库 `net/http` 调用 Mihomo `external-controller` 的 HTTP API，读取版本、代理、连接、流量、日志和延迟信息，并执行配置加载、配置重载和节点选择。Bagualu 不导入 Mihomo 源码、`core` 包或其他内部 Go 包。
- **代理端口调用**：Bagualu 的连通性请求和下载测速程序连接 Mihomo 暴露的本地 HTTP/SOCKS/Mixed 端口，确保测试流量经过指定节点。
- **结果计算**：Bagualu 只使用 Mihomo HTTP API 返回的连接链路和流量数据，以及应用层代理请求数据；Bagualu 使用实际下载字节数与有效耗时计算最终速度并保存结果。

不采用把 Mihomo 源码或 `core` 包嵌入 Bagualu 进程的方式。除启动、停止和监督 Mihomo 子进程外，Mihomo HTTP API 是 Bagualu 与内核之间唯一的运行时功能控制契约；直接源码耦合会增加 OpenWrt 编译、升级、内存占用和崩溃隔离成本。

Mihomo 内核依赖包需要满足以下要求：

- 采用成熟、协议覆盖范围广的代理核心，覆盖项目确认范围内的节点协议。
- 由 Bagualu 通过配置和进程参数启动，并由 Bagualu 通过 HTTP 控制 API 和本地代理端口调用。
- 第一版固定只运行一个 Bagualu 管理的 Mihomo 进程；该进程支持多个相互隔离的逻辑测试连接并返回原始连接和流量数据，不得为每个测试任务创建独立 Mihomo 进程，也不得由 LuCI 单独拉起第二个进程。
- 由于单进程内通过 HTTP API 切换代理组会改变共享选择状态，所有节点测速任务必须使用单线程队列执行，同一时刻最多只有一个节点处于测速状态。禁止通过增加 Goroutine、任务 worker、Mihomo 进程或代理端口实现并发测速。
- 能够通过 HTTP API 被 Bagualu 查询版本、支持协议、运行状态、连接数和资源占用。
- 不注册独立 OpenWrt 服务，不提供独立 LuCI 控制入口，不承担 Bagualu 任务状态或业务 API。

第一版内核依赖确定采用 **Mihomo（原 Clash.Meta）**。不采用已经停止维护的旧版 Clash 核心。Mihomo 只负责节点协议连接、代理转发、连接信息和流量统计，Bagualu 负责订阅、任务调度、测速计算、结果保存和页面展示。

OpenClash 是 OpenWrt 上的 LuCI 管理插件，不是代理核心本身。OpenClash 通常管理 Mihomo/Clash 系列核心，因此 Bagualu 与 OpenClash 可以使用同一核心家族和相近配置格式，但两者不是同一个服务。

Bagualu 不得直接接管或重载 OpenClash 正在运行的核心实例。默认部署方式为：

- Bagualu 携带或安装自己兼容架构的 Mihomo 可执行文件。
- Bagualu 默认使用自身独立路径下的 Mihomo 二进制，不覆盖、不替换、不升级 OpenClash 的核心文件。
- Bagualu 使用独立的 Mihomo 进程、配置目录、控制端口和本地代理端口。
- Mihomo 控制 API 和测速代理端口默认只监听 `127.0.0.1`，控制 API 使用独立密钥，仅允许 Bagualu 调用。
- Bagualu 管理的 Mihomo 进程不修改 OpenClash 配置，不停止 OpenClash，不占用 OpenClash 端口。
- 当 OpenClash 与 Bagualu 同时运行时，页面必须检测并提示端口冲突和内存占用风险。
- 第一版不提供系统 Mihomo 二进制复用选项；后续若增加该能力，必须单独评审包依赖、版本兼容和共存边界，且仍不得接管其他服务的进程或配置。

#### 4.3.1 与 OpenClash 共存的硬性约束

Bagualu 安装和运行后不得改变 OpenClash、PassWall、HomeProxy 等现有代理服务的配置、进程、网络规则和流量路径。第一版测速采用“本地显式代理”模式，不使用透明代理模式。

- 使用独立的 OpenWrt 服务名、进程 PID 文件、配置目录、数据目录、日志标识和临时目录。
- Mihomo 控制 API、Mixed/HTTP/SOCKS 测速入口只监听 `127.0.0.1`，不得监听 LAN 或 WAN 地址。
- 安装时动态检查端口占用；默认端口冲突时自动分配可用端口并保存配置，不得停止占用端口的其他服务。
- 不启用 Mihomo TUN、Redir、TProxy、Fake-IP DNS、系统代理或 LAN 访问能力。
- 不写入或修改 nftables、iptables、ip rule、ip route、dnsmasq、DHCP、默认路由和 DNS 配置。
- 不读取、覆盖、重载或删除 OpenClash 的运行配置与订阅数据。
- 不向 OpenClash 控制 API 发送修改、切换节点、重载或停止指令。
- Bagualu 停止或卸载后，只清理自身进程、配置和临时资源，不影响 OpenClash 当前连接。
- 同时运行时限制 Bagualu 所管理 Mihomo 内核的逻辑连接数、测速队列长度、内存和测速流量；达到设备资源门槛后暂停新任务并在页面告警。测速执行始终保持单线程。

启动前必须执行共存检查：服务名、进程、控制端口、代理端口、配置目录、可用内存和 OpenClash 状态。检查发现风险时，只阻止 Bagualu 管理的 Mihomo 依赖进程启动，不得对其他服务采取修复动作。

卸载验收必须确认：OpenClash 服务状态未变化，OpenClash 配置文件未变化，系统防火墙、路由和 DNS 未被 Bagualu 修改。

#### 4.3.2 全协议支持定义

“支持全协议”定义为：覆盖当前安装的 Mihomo 版本所支持的全部节点协议、传输方式和协议参数，而不是承诺支持世界上所有代理协议。

- 系统启动时读取 Mihomo 版本，并形成对应的协议能力清单。
- 订阅解析器必须完整保留 Mihomo 节点字段，不能只提取地址、端口等基础字段。
- Clash/Mihomo YAML 节点优先使用结构化解析和字段透传，保持协议、TLS、传输层和插件参数。
- URI/Base64 订阅转换为统一节点模型后，再由 Mihomo 适配器生成核心配置。
- 第一版协议范围至少覆盖 Mihomo 当前支持的主流协议，包括 SS、SSR、VMess、VLESS、Trojan、HTTP、SOCKS5、Snell、WireGuard、Hysteria/Hysteria2、TUIC、SSH 以及 Mihomo 后续兼容协议。
- 每种协议都必须通过“配置加载测试 + 协议级连通性测试”后才能标记为已支持。
- Mihomo 支持但 Bagualu 暂未解析的节点标记为 `parser_unsupported`；Mihomo 本身不支持的节点标记为 `core_unsupported`。
- 不支持的节点可以保留并展示原始来源与原因，但不得进入测速成功结果或可用资源输出。

Bagualu 管理后台需要展示当前 Mihomo 版本的协议能力矩阵，包括：可解析、可加载、可连通测试、可下载测速及失败原因。Mihomo 升级后由 Bagualu 自动重新检测能力，不在代码中固定一份永久不变的协议列表。

Bagualu 内核适配层至少需要提供以下能力：

- 将统一节点配置转换为 Mihomo 配置。
- 按节点或测试任务创建隔离的临时逻辑连接和配置实例，不创建独立 Mihomo 进程。
- 检查由 Bagualu 管理的 Mihomo 进程状态；由 Bagualu 主程序负责按需拉起或停止 Mihomo。
- 使用 Go `net/http` 调用 Mihomo HTTP 控制 API，统一处理鉴权、超时、状态码、响应 JSON 和错误码。
- 通过 HTTP API 完成版本读取、配置加载/重载、节点选择、连接查询、流量查询、延迟测试和日志读取。
- 为测试任务提供 Bagualu 管理的 Mihomo 进程内的本地代理入口。
- 把连通性测试和下载测速请求导向指定节点。
- 获取实际连接状态、请求耗时、下载字节数和错误信息。
- 测试完成后释放本次逻辑连接、临时配置和临时文件；不得因单个测试完成而停止或重启 Mihomo 内核。所有节点测试必须串行执行，避免通过 HTTP API 切换共享代理组造成节点选择竞态。

Bagualu 内核适配层第一版实现 Mihomo 配置生成器、子进程管理器、HTTP API 客户端和本地代理请求客户端；Mihomo 进程监督由 Bagualu 应用层调用 `infrastructure/mihomo` 完成，LuCI/procd 只监督 Bagualu 主程序。上层页面、任务 API、测试结果和资源 API 不直接依赖 Mihomo 私有配置格式，以便未来升级 Mihomo 版本。

### 4.4 Mihomo HTTP API 测试契约

所有协议级连通性测试和实际下载测速都必须经过由 Bagualu 管理的 Mihomo 进程，并由 Bagualu 通过 Mihomo HTTP 控制 API 和本地代理端口完成。该要求属于硬性系统契约，不允许在实现中回退成系统直连、仅测试目标端口、直接链接 Mihomo `core` 包或使用其他网络出口。

每次测试必须执行以下链路：

1. Bagualu 校验节点协议和必要参数；启动阶段生成 Bagualu 专用 Mihomo 配置并加载全部待测节点，不为每个节点创建配置文件和进程。
2. Bagualu 启动或复用自己管理的 Mihomo 进程，仅通过 `127.0.0.1` 的 HTTP 控制 API 完成版本和健康检查，记录 Mihomo PID、控制 API 地址、代理端口和配置版本。
3. 配置新增或变更时，Bagualu 先调用 Mihomo 已验证的配置检查/加载接口，再按需 reload；配置变更不是每次节点测试的必经步骤。HTTP 状态码不是成功状态、响应 JSON 无效或配置校验失败时，任务直接失败。
4. Bagualu 通过 Mihomo HTTP 代理管理接口确认节点已加载，并通过 HTTP API 选择本次任务的唯一节点；选择、代理请求和结果采集必须由同一把任务锁保护。
5. Bagualu 将本次任务绑定到唯一节点，记录测试前的连接数和流量计数。
6. 测试程序只允许连接 Bagualu 为本次逻辑测试分配的 Mihomo 本地 HTTP/SOCKS/Mixed 代理端口，通过该端口发起连通性请求或下载请求。
7. Bagualu 通过 Mihomo HTTP API 查询该任务对应的连接链路、节点名称和流量变化，并校验实际出口。
8. 只有“测试请求成功、指定节点链路可确认、Mihomo 流量增加”同时成立时，测试才允许标记为成功。
9. Bagualu 保存结果和内核证据摘要，随后关闭本次代理连接并回收任务状态；不得删除共享配置、释放共享端口或停止 Mihomo 进程。

失败规则：

- Mihomo 可执行文件不存在、无法启动或异常退出：任务失败，错误为 `core_unavailable`。
- Mihomo HTTP 控制 API 不可访问、HTTP 超时、鉴权失败、返回非预期状态码或响应格式错误：任务失败，错误为 `core_api_unavailable`。
- 节点未被 Mihomo 正确加载：任务失败，错误为 `node_load_failed`。
- 测试请求未经过指定节点、无法确认连接链路或内核流量没有变化：任务失败，错误为 `core_route_unverified`。
- 代理请求失败或超时：按连接阶段记录失败，不得改用 OpenWrt 默认出口重试。

每条成功测试结果必须保存以下内核证据摘要：Mihomo 版本、受管实例 ID、配置摘要、目标节点 ID、Mihomo 中的节点名称、连接 ID、出口地址、测试前后流量差值和测试时间。敏感节点参数不得写入证据摘要或普通日志。

#### 4.4.1 HTTP API 调用边界

Bagualu 与 Mihomo 的运行时集成只允许使用以下两类本地接口：

1. **控制 API**：使用 Go 标准库 `net/http` 调用 `http://127.0.0.1:<control-port>`，通过 Bearer Token 鉴权。请求必须设置连接、响应头和整体超时，限制响应体大小，并统一校验 HTTP 状态码和 JSON 结构。
2. **代理入口**：使用 Go 标准库 `net/http` 的 `Transport`/`DialContext` 通过 Mihomo 本地 HTTP、SOCKS 或 Mixed 端口发送测试请求。测试请求不得绕过该代理入口访问节点或测试站点。

控制 API 客户端至少覆盖：`GET /` 健康检查、`GET /version` 版本、`GET /proxies` 节点状态、`GET /proxies/{name}` 节点详情、`PUT /proxies/{group}` 节点选择、`GET /proxies/{name}/delay` 协议级延迟、`GET /connections` 连接证据、`GET /traffic` 流量证据，以及配置加载/重载所需的 Mihomo HTTP 接口。具体路径和字段必须以锁定的 Mihomo 版本 API 契约测试为准，不得凭猜测硬编码未验证字段。

HTTP 客户端必须复用连接池和 Transport，不得每次请求创建新的 `http.Client` 或连接池；控制请求并发限制为低数量，响应只解码需要的字段；连接和流量轮询使用退避、采样间隔和最大响应大小。Mihomo 日志由子进程输出到 Bagualu 日志管道，不通过高频 HTTP 轮询读取。

禁止事项：

- 禁止导入 Mihomo `core` 包、源码目录、内部 Go 包或通过 `replace` 指令嵌入 Mihomo 源码。
- 禁止在 Bagualu 中重新实现 SS、VMess、VLESS、Trojan、Hysteria、TUIC 等代理协议。
- 禁止使用 shell/curl 作为业务调用路径；进程启动参数可以由 `os/exec` 管理，但 HTTP 控制必须由 Go 客户端完成。
- 禁止为每个节点创建一个 Mihomo 进程；第一版复用一个受管进程，按任务隔离配置、节点选择和连接证据。

这样做的资源边界是：一个 Mihomo 进程承担协议开销，Bagualu 只增加一个轻量 HTTP 客户端、有限数量的代理连接和少量 JSON 结果内存；Mihomo 崩溃不会拖垮 Bagualu 主进程，Mihomo 升级也不要求重新编译 Bagualu。

#### 4.4.2 `mihomo-speedtest-rs` 参考实现结论

参考项目 [mihomo-speedtest-rs](https://github.com/KodeBarinn/mihomo-speedtest-rs) 的 Mihomo 模式采用外部进程调用，不是代码级链接：

- `MihomoRunner` 创建临时配置目录，生成包含节点和 `SpeedTest` 选择组的 YAML。
- 通过 `Command` 启动 Mihomo 子进程，并将 `external-controller`、Mixed 代理端口绑定到 `127.0.0.1`。
- 使用 HTTP API `GET /` 做健康检查，`PUT /proxies/SpeedTest` 切换节点，`GET /proxies/{name}` 读取节点信息，`GET /proxies/{name}/delay` 调用 Mihomo 延迟测试。
- 使用本地代理端口创建 HTTP 客户端，实际下载请求经 Mihomo 转发；项目没有导入 Mihomo `core` 包。
- 项目的 `isolated-lanes` 模式会为每个 lane 创建独立 Mihomo 进程和端口，隔离性更强但资源开销线性增加，不适合 Bagualu 第一版的单进程低资源目标。

Bagualu 采用该项目的 HTTP 控制思路，但不直接复制其会话模型：Bagualu 长驻一个受管 Mihomo 进程，启动时加载节点配置，测试时通过 HTTP API 选择节点并通过本地代理端口测试；所有测速任务严格串行，避免共享 `SpeedTest` 选择组被并发切换。参考项目的多 lane 并行模式不适用于 Bagualu，第一版及后续版本均禁止并发测速。

## 5. OpenWrt 服务需求

### 5.1 服务要求

系统必须以 OpenWrt 服务形式安装和运行，不能只提供 Docker 或普通开发机启动方式。

服务需要支持：

- 安装后注册为 OpenWrt init 服务。
- 开机自动启动。
- `start`、`stop`、`restart`、`reload`、`status` 操作。
- 异常退出后自动拉起。
- LuCI 主页面只负责统一启用、禁用、启动、停止和重启 Bagualu 主程序；Bagualu 主程序负责内部 Mihomo 内核的启动、停止、重启、端口和健康检查。
- Bagualu 管理端口与 Mihomo 控制/代理端口相互独立，端口冲突时由 Bagualu 检查并向 LuCI 页面报告。
- 使用 OpenWrt 配置目录保存配置和数据。
- 使用 OpenWrt 日志机制输出运行日志。
- 支持配置管理页面监听地址、管理端口、Mihomo 控制端口和本地测速代理端口、数据目录、管理员认证和任务开关。
- 在低内存设备上限制测速队列长度、单次测速流量和历史数据量；测速执行仍固定为单线程。

LuCI 的 Bagualu 主服务启用开关是唯一服务开关：开启后由 procd 拉起 Bagualu 主程序，Bagualu 再自动启动并管理 Mihomo 内核。LuCI 不把 Mihomo 注册为独立 init 服务，也不直接启动或停止 Mihomo。Mihomo 内核异常时由 Bagualu 自动重启；连续失败时 Bagualu 进入 `degraded` 或 `failed`，并将具体原因上报 LuCI。

### 5.1.1 服务生命周期与进程监督

服务生命周期由 LuCI、UCI、ubus 和 procd 共同负责，HTTP 管理 API 不直接执行 Bagualu 主程序自身的停止、重启或拉起；Mihomo 生命周期由 Bagualu 主程序负责。

服务关系固定如下；LuCI/procd 只监督 Bagualu 主程序，Mihomo 是 Bagualu 的内部受管子进程：

```text
LuCI 页面
   |
   v
ubus -> procd -> Bagualu 主程序 -> Mihomo 内核进程
                         |              |
                         |              +-> 控制端口、代理端口
                         +-> 管理端口、HTTP API、任务调度
```

- LuCI 的“启用/禁用”开关写入 Bagualu 独立 UCI 配置，并通过 ubus 调用 procd；LuCI 不直接拼接 shell 命令。
- “启用”表示允许 Bagualu 主程序随 OpenWrt 启动并持续运行。procd 启动 Bagualu 后，Bagualu 依次检查共存条件、端口和 Mihomo 可执行文件，再启动 Mihomo 并完成控制 API 握手。
- “禁用”表示持久化关闭 Bagualu 自动启动和异常自动拉起。执行禁用时，LuCI 通过 ubus 请求 procd 停止 Bagualu；Bagualu 收到停止信号后先停止自己管理的 Mihomo，再关闭自身端口和退出，不影响 OpenClash 或其他服务。
- “启动/停止/重启”是一次性运行控制，不改变“启用/禁用”持久开关。手动停止属于受控停止，不视为异常退出，procd 不得立即自动拉起；启用配置仍保留，设备下次启动时按启用配置自动启动。重启则直接执行停止后启动。
- procd 只监督 Bagualu 主程序；Bagualu 主程序独立监督自己启动的 Mihomo 子进程，不接管其他服务或其他 Mihomo 实例。
- Bagualu 主程序异常退出时由 procd 自动拉起；Mihomo 异常退出时由 Bagualu 按退避策略自动重启。Mihomo 连续失败达到阈值时，Bagualu 保持主程序运行但进入 `degraded`，暂停节点测试并显示 `core_unavailable`。
- 连续崩溃达到阈值时停止重启并进入 `failed` 状态，避免死循环消耗 CPU、闪存和日志空间；必须由 LuCI 展示失败原因并允许管理员重新启动或执行诊断。
- Bagualu 启动必须依次完成 UCI 配置读取、架构和可执行文件检查、OpenClash 共存检查、管理端口和 Mihomo 端口检查、数据目录检查、Bagualu 管理端口监听、Mihomo 启动及控制 API 握手。任一步失败都不得报告 Bagualu 为“运行中”。
- Bagualu 管理端口未成功监听时，LuCI 仍可通过 ubus/procd 获取 Bagualu 和 Mihomo 状态、显示启动错误并执行重试、启动、停止或禁用；不依赖 Bagualu HTTP API。

Bagualu 服务状态至少包括：`disabled`、`starting`、`running`、`stopping`、`degraded`、`failed` 和 `stopped`。状态必须同时返回 Bagualu 期望状态、实际状态、Mihomo 内核状态、最近操作 ID、最近错误码、最近错误时间、Bagualu PID、Mihomo PID、管理端口、控制端口、代理端口和 Mihomo 自动拉起次数。

所有生命周期操作必须返回异步操作结果：LuCI 点击后立即显示“已提交”，获得 `operation_id`，随后通过 ubus 状态查询或受控状态接口轮询，直到操作进入 `succeeded`、`failed` 或 `cancelled`。不得要求停止/重启请求依赖原 HTTP 连接保持成功，也不得把 HTTP 连接断开视为操作失败。

默认自动拉起策略：Bagualu 主程序由 procd 负责拉起；Mihomo 由 Bagualu 主程序负责拉起。每次失败记录组件名、退出码、信号、最后日志摘要和重启次数；Mihomo 达到失败阈值后，Bagualu 进入 `degraded` 或 `failed`，等待管理员通过 LuCI 重试或重启 Bagualu。

### 5.2 OpenWrt LuCI 配置页面

安装包必须在 OpenWrt LuCI 中注册独立菜单入口。LuCI 页面保持轻量，只负责服务安装后的基础控制和诊断；节点管理、报表等复杂功能进入 Bagualu 独立管理后台。

LuCI 页面提供以下运行配置：


| 配置项 | 说明 |
| --- | --- |
| 服务状态 | 显示运行、停止或异常状态。 |
| 管理服务状态 | 显示 Bagualu 管理服务是否启用和运行。 |
| Mihomo 内核状态 | 显示内核依赖包是否已安装、Bagualu 管理的 Mihomo 进程是否运行、异常或未就绪。 |
| Mihomo 信息 | 显示 Mihomo 版本、支持架构、控制 API 连通状态和可执行文件来源。 |
| OpenClash 共存检查 | 检查 OpenClash 运行状态、端口冲突和资源占用风险。 |
| 监听地址 | 管理页面和管理 API 监听地址。 |
| 管理端口 | 管理页面和管理 API 端口。 |
| Mihomo 端口 | Mihomo 控制 API 和本地测速代理入口端口；默认仅本机可访问，由 Bagualu 分配和管理。 |
| 开机启动 | 是否随 OpenWrt 启动。 |
| 数据目录 | 节点和测试数据保存位置。 |
| 测速执行方式 | 固定单线程，同一时刻只允许一个节点执行测速；其他节点进入队列等待。 |
| 允许测速时段 | 配置一个或多个本地时间段；非时段内任务等待，不计为节点失败。 |
| WAN 带宽 | 配置出口上行和下行带宽；未配置时显示容量未知。 |
| 出口负载阈值 | 配置测速前后允许的上行、下行背景利用率；超过阈值时暂停或排除测速。 |
| 测速源 | 配置一个或多个独立测速文件地址，并显示测速源健康状态。 |
| 日志级别 | 支持正常、详细和错误级别。 |
| 测试任务开关 | 分别控制连通性、Ping 和每日测速任务。 |
| 管理员账号 | 设置管理员登录账号。 |
| 管理员密码 | 设置或修改管理员登录密码。 |
| 打开管理后台 | 使用按钮在新页面打开 Bagualu 管理后台，不要求用户手工输入地址和端口。 |

页面必须提供明确的“启用/禁用”“启动”“停止”“重启”操作，并显示异步操作状态。页面需要分别展示“期望状态”和“实际状态”：例如已启用但启动失败时显示“已启用/启动失败”，并显示错误码、失败阶段、最近日志摘要和“重新启动”“运行诊断”入口。Mihomo 依赖进程未就绪时，订阅管理和页面访问仍可用，但节点测试任务应进入暂停或失败状态并给出原因；LuCI 不提供单独的 Mihomo 启用开关。

LuCI 服务控制规则：

- LuCI 通过 ubus/procd 只控制 Bagualu 主程序，不依赖 Bagualu 管理端口是否已监听。
- 启用操作先保存 Bagualu UCI 配置，再请求 procd 启动 Bagualu；Bagualu 自身按“检查环境、监听管理端口、启动 Mihomo、确认 Mihomo 就绪”的顺序执行。任一检查失败时保留“已启用”配置，但 Bagualu 实际状态显示 `failed` 或 `degraded`，并将失败原因返回 LuCI。
- 禁用操作先更新 Bagualu 启用状态，再请求 procd 停止 Bagualu；Bagualu 按“停止测试任务、停止 Mihomo、关闭自身端口、退出”的顺序执行，完成后状态为 `disabled`，不得因 procd 的异常自动拉起再次启动。
- 手动停止操作不修改 UCI 启用状态，停止完成后 Bagualu 实际状态为 `stopped`，同时 Mihomo 必须已退出；在管理员再次点击启动/重启前不得自动拉起。
- 重启操作保留当前启用状态，按“停止 Bagualu、回收 Mihomo、重新启动 Bagualu、由 Bagualu 启动 Mihomo、确认 Mihomo 就绪”的顺序执行；OpenClash 和其他服务不参与该流程。
- LuCI 页面通过轮询状态或 ubus 事件刷新状态，不等待管理后台 HTTP 请求返回来判断启停是否完成。

LuCI 页面还必须显示：Bagualu 版本、Mihomo 版本、OpenClash 是否运行、共存检查结果、端口冲突、最近错误和管理后台可访问状态。“打开管理后台”按钮仅在后台可访问时启用；不可访问时显示具体修复提示。

### 5.3 配置隔离与升级

- Bagualu 使用独立 UCI 配置命名空间，不复用 OpenClash 的 UCI section。
- 升级 Bagualu 时保留管理员设置、上游、节点、分组、API Key 和测试历史。
- 升级 Mihomo 前进行架构和版本校验，失败时保留当前可用版本。
- 服务配置变化需要明确提示“立即生效”或“需要重启”，不能静默重启 OpenClash 或其他服务。
- 管理员密码只保存安全摘要，LuCI 页面和日志不得回显密码。

## 6. 核心业务对象

| 对象 | 说明 |
| --- | --- |
| 上游订阅 | 代理节点的来源，包含订阅名称、地址、格式和刷新配置。 |
| 节点 | 从上游解析出的单个代理配置，包含协议、地址、端口和协议参数。 |
| 分组 | 一组节点的集合，可用于不同用途或不同 API 客户端。 |
| 订阅链接 | 对外发布资源的稳定链接，绑定一个资源分组、访问凭证和默认输出策略。 |
| 测试结果 | 某个节点某次连通性、Ping 或下载测速的结果。 |
| 节点评分 | 基于延迟、速度和可用率三个维度计算的子分及 0–100 综合分。 |
| IP 归属地 | 根据节点真实代理出口 IP 识别的国家/地区、城市和网络运营信息。 |
| API Key | 外部客户端访问指定分组资源的凭证。 |
| 后台任务 | 订阅刷新、节点测试和数据维护任务。 |
| 运行实例 | 当前 Bagualu 管理的 Mihomo 内核进程及其逻辑测试连接，包含状态、节点、连接和流量信息。 |
| 流量报表 | 按时间、节点、分组和协议统计的测速流量和结果。 |
| 系统日志 | Bagualu 主程序和其管理的 Mihomo 内核进程运行日志。 |

### 6.1 节点状态

节点需要至少支持以下状态：

- `active`：节点存在且可参与测试和分组资源输出。
- `unreachable`：最近连通性测试失败。
- `endpoint_ip_unreachable`：同一入口 IP 被共享网络层探测判定为暂时不可达；该状态不代表单个协议配置错误，也不产生重复失败样本。
- `disabled`：管理员手动禁用。
- `expired`：节点已不在有效上游订阅中。
- `invalid`：节点配置解析失败或配置不完整。

节点状态和测试结果分开保存。Ping 成功不能直接将节点标记为可用，下载速度也不能替代连通性状态。

### 6.1.1 节点去重与 IP 过滤

节点去重必须区分“入口 IP”与“真实出口 IP”：

- **入口 IP**是节点配置中用于连接代理服务器的地址，用于订阅合并和重复候选分组。
- **真实出口 IP**是通过节点代理访问外部查询服务得到的地址，可能因 NAT、落地线路或节点策略变化，不作为节点唯一键。
- 仅使用 IP 作为唯一键会误删同一服务器上不同端口、不同协议、不同账号或不同传输参数的有效节点，因此 IP 只能作为候选过滤维度，不能单独决定删除节点。

节点解析后必须执行规范化：域名保持原始域名并记录解析到的地址；IPv4、IPv6 使用标准文本格式；协议名称、端口、TLS、传输层、SNI、Host、路径、插件和认证参数统一格式化。敏感认证字段只参与哈希，不得明文写入去重键或日志。

去重规则如下：

1. **精确重复合并**：协议、入口地址、端口、认证参数摘要和全部影响连接的传输参数一致时，视为同一个逻辑节点。系统只保留一个节点记录，合并其上游来源、原始名称和来源片段，测试历史不重复执行。
2. **同 IP 候选分组**：入口 IP 相同但端口、协议、认证或传输参数任一不同的节点，归入同一 `endpoint_ip_group`，但仍保留为独立节点并分别测试。不得仅因 IP 相同而删除。
3. **资源输出去重**：订阅或资源 API 默认启用“每个入口 IP 只输出一个节点”策略。每个 IP 组先过滤禁用、未评分、综合分低于 60、最近协议测试失败和不兼容节点，再保留综合分最高的 `recommended` 节点。分数相同时依次比较可用率分、延迟分、速度分，最后使用稳定节点 ID 确定结果。
4. **后台完整保留**：去重只影响逻辑合并或外部资源输出，不删除原始节点、来源关系和测试历史。管理员可以关闭“每 IP 一个节点”策略，输出同一 IP 下的多个不同协议或端口节点。
5. **节点状态变化**：节点入口 IP、端口、协议或关键连接参数变化时生成新的节点指纹，旧节点保留为历史记录并重新进入 `unrated`，不得继承旧节点评分。

默认去重策略为“精确重复合并 + 资源输出每入口 IP 保留最佳推荐节点”。页面必须展示同 IP 下被隐藏的节点、保留节点及其隐藏原因，例如“同入口 IP 下综合分较低”。

### 6.1.2 IP 共享故障域与测试优化

同一入口 IP 下的节点共享主机、路由和部分网络条件，因此测试调度采用两级判断：

- **共享网络层故障**：如果 Bagualu 观察到明确的 `network_unreachable`、`host_unreachable`，或同一入口 IP 下多个节点在协议握手前出现一致的底层连接失败，则打开该 IP 的熔断状态 `endpoint_ip_unreachable`。熔断期间，该 IP 下所有节点暂停测试并从外部资源隐藏，页面显示“同入口 IP 不可达”；不得为每个节点重复发起相同测试。
- **端口级故障**：TCP 连接被拒绝、单个端口超时或 UDP 端口无响应，只能先标记对应的 IP+端口端点，不得直接推断该 IP 上所有其他端口都不可用。
- **协议级故障**：TLS、认证、VMess/VLESS/Trojan 握手、传输层参数或 Mihomo 配置错误只影响当前节点，不得因为同 IP 的一个协议失败而隐藏其他节点。
- **恢复检查**：IP 熔断经过退避时间后只允许先测试一个代表节点；代表节点完成底层连接并通过协议验证后，再逐步恢复该 IP 下其他节点测试。恢复前的熔断结果不计入任何节点的可用率分母。

同一 IP+端口的节点可以共享网络层连通性结果，但速度仍必须按节点实际测试保存。协议加密、传输方式、认证账号、服务端限速和线路策略都可能不同，不能直接把一个节点的速度复制给其他节点。调度器可以先测试该 IP 组内当前综合分最高的代表节点，用于判断是否值得继续测试；代表节点成功后再测试其他协议节点。

IP 熔断只是一种临时运行状态，不删除节点、不合并不同协议配置，也不覆盖节点原有评分。资源输出仍按 6.1.1 的“每入口 IP 保留最佳推荐节点”规则执行。

### 6.2 订阅链接

订阅链接是 API Key 之外面向代理客户端的直接访问方式。每条订阅链接必须：

- 绑定一个资源分组，访问者只能获取该分组及其自动派生地区组中的节点。
- 使用不可预测的随机 Token，不在 URL 中暴露数据库 ID 或 API Key。
- 支持启用、禁用、轮换 Token、设置有效期和最后访问时间。
- 配置默认输出格式、节点排序、最低评分、节点数量上限和健康过滤策略。
- 支持通过允许的查询参数临时覆盖输出格式，但不能绕过分组授权和过滤策略。
- 页面提供可复制链接、二维码、最近访问状态和立即失效操作。

订阅链接与 API Key 分开管理：API Key 面向程序化 API 调用，订阅链接面向 Clash/Mihomo、sing-box、dae/daed 等客户端直接更新订阅。

### 6.3 IP 归属地

- 节点归属地必须优先使用通过该节点访问 IP 查询服务得到的真实代理出口 IP，不能只使用节点服务器域名解析出的 IP。
- 保存出口 IP、国家/地区代码、国家/地区名称、城市、ASN、网络组织、数据来源和更新时间。
- 同一节点出口 IP 变化时重新查询归属地，并保留最近一次变更时间。
- IP 查询失败时标记为“未知地区”，不能根据节点名称猜测并覆盖真实结果。
- 可将节点名称中的地区词作为低可信提示，用于出口测试前的临时展示；一旦取得真实出口结果，以出口归属地为准。
- IP 数据库或外部查询服务需要可替换，并支持本地数据库优先，避免 OpenWrt 长期依赖公网 API。

## 7. 节点测试需求

系统必须提供三类测试，三类测试独立调度、独立记录、独立展示。

### 7.1 协议级连通性测试

作用：验证节点能否按照自身协议建立连接并访问测试地址。

要求：

- 必须根据节点协议建立真实连接。
- 测试任务将节点配置和测试参数交给 Bagualu 内核适配层，由 Bagualu 管理的 Mihomo 内核进程完成协议连接。
- 不能只测试节点地址端口是否开放。
- 测试成功后记录成功状态、耗时和测试时间。
- 测试失败后记录失败原因和失败阶段。
- 需要记录 Mihomo 返回的连接阶段、出口信息和请求结果。
- 连通性结果用于判断节点是否可以进入可用资源。

### 7.2 Ping 延迟测试

作用：定时观察节点地址的网络延迟。

要求：

- 定时执行，默认每分钟一次，可配置。
- 记录延迟、丢包和测试时间。
- 支持在 OpenWrt 环境下使用可用的 Ping 方式。
- Ping 结果只代表延迟表现，不代表代理协议一定可用。

### 7.3 实际下载测速

作用：测量通过节点代理连接后的真实下载速度。

要求：

- 必须按照节点协议连接成功后，再通过该连接实际下载测试文件。
- Bagualu 测速程序负责生成测速参数，Mihomo 内核进程负责建立节点代理连接和承载下载请求。
- 默认每个节点每天测试一次。
- 测试文件地址、测试时间窗口、单次最大下载量和超时时间可配置。
- 调度器必须按入口 IP 进行共享健康预检查；同一 IP 被判定为共享网络层不可达时，暂停该 IP 下其他节点测试，避免重复消耗连接和流量。
- 记录实际下载速度、下载量、耗时、首字节时间、测试时间和失败原因。
- 速度必须根据实际下载字节数和有效下载耗时计算，不能使用代理节点声明的带宽值。
- 如果 Mihomo 能够提供连接级流量统计，系统应优先使用内核统计作为测速依据，并同时保留应用层统计。
- 测速结果必须显示测试时使用的节点和协议。
- 测速结果必须显示“已由 Mihomo 验证”的状态和可追踪的内核证据摘要。
- 测速失败不能覆盖上一次成功的速度结果。
- 系统需要限制测速队列长度、单次测速流量和总流量，避免影响 OpenWrt 正常网络使用。
- 所有协议连通性测试、Ping 和下载测速共用单线程测试队列；同一时刻只允许一个节点执行测试，禁止任何并发测速行为。该限制不是可配置项。

测速任务完成后，Bagualu 内核适配层需要向 Bagualu 业务层返回统一结果：任务状态、节点 ID、代理协议、测试地址、连接耗时、首字节耗时、下载字节数、有效下载耗时、下载速度、出口地址和失败原因。页面和 API 只使用统一结果，不直接依赖 Mihomo 的返回格式。

### 7.4 测试策略

系统支持全局默认测试策略，也支持分组覆盖默认策略。策略至少包括：

- 是否启用该类测试。
- 执行周期。
- 超时时间。
- 测试地址。
- 测试队列长度上限；测速执行线程数固定为 1，不提供并发数量配置。
- 允许测速时段。
- WAN 上行带宽、下行带宽和测速负载保护阈值。
- WAN 接口识别方式和负载无法获取时的处理方式。
- 测速源列表和测速源健康检查策略。
- 节点纳入测试的条件。
- 节点进入资源输出的最低要求。

#### 7.4.1 单线程测试调度契约

- Bagualu 只有一个节点测试执行队列，协议连通性、Ping 和下载测速任务必须统一排队。
- 测速执行线程数固定为 1；同一时刻最多执行一个节点的一项测试，禁止节点之间、测试类型之间和重试任务之间并发。
- 新任务只能进入队列等待，不能创建额外 worker、Goroutine、进程或代理端口绕过单线程限制。
- 当前任务未完成、超时、取消或释放 Mihomo 连接前，调度器不得开始下一个节点任务。
- 手动测试、定时测试和失败重试必须复用同一个队列和同一把执行锁。
- 页面只展示队列长度、当前节点、当前测试类型和预计状态，不提供并发数量配置。

该限制用于保证测速结果可比较、避免共享 Mihomo 代理选择状态被切换，并减少路由器资源和出口带宽竞争。后续需求也不得默认放开并发测速；如需变更，必须先修改本节并重新定义测试隔离和准确性验收标准。

#### 7.4.2 测试前外网基线检查

为区分“路由器自身外网中断”和“代理节点不可用”，每一轮协议测试、Ping 测试和下载测速开始前，必须先执行外网基线检查。该检查使用 OpenWrt 默认网络出口，不能经过 Bagualu 管理的 Mihomo 实例或任何待测节点。

默认检查目标为 `www.baidu.com`，检查参数如下：

- 先解析目标域名；域名解析失败时，检查失败，错误码为 `network_baseline_unavailable`。
- 发送 3 次 ICMP Echo 请求，单次超时 2 秒，连续两次检查之间间隔 1 秒。
- 至少收到 1 次有效响应，且往返时间不超过超时值，才判定本轮外网基线可用。
- 目标地址、探测次数、单次超时和重试间隔必须可配置；默认目标仍为 `www.baidu.com`。
- 本轮必须以 `www.baidu.com` 的 ICMP Echo 响应作为外网基线；不允许使用 HTTPS 回退替代 Ping。若设备或运营商禁止 ICMP，基线检查失败，必须暂停节点测试并告警。

外网基线检查失败时，当前轮次的所有节点测试任务进入 `paused` 或 `skipped` 状态，错误码为 `network_baseline_unavailable`，不得执行节点测试，并且：

- 不得把节点标记为 `unreachable` 或 `unavailable`。
- 不得覆盖最近一次成功的连通性、延迟、速度、可用率和综合评分。
- 不得重算节点评分，也不得产生节点失败样本。
- 任务记录必须保存探测目标、探测方式、解析结果、响应次数、耗时、失败原因和时间。
- 页面和运行后台必须显示“外网基线不可用，已暂停节点测试”，并显示最近一次成功基线检查时间。

调度器在基线恢复后才能继续节点测试。恢复时必须连续两次基线检查成功，且两次检查间隔至少 1 秒；恢复前已经排队的节点任务可以继续执行，但必须重新执行一次基线检查，不能使用旧检查结果直接放行。

节点测试开始后若外网基线在任务期间失效，只终止或标记当前任务为 `network_baseline_lost`，不将该结果计入节点可用率，不改变节点状态和评分。外网基线自身的失败属于基础设施错误，不得归因于节点。

#### 7.4.3 出口网络负载保护与测速时段（建议方案）

测速结果同时受节点能力、测试服务器能力和路由器当前出口负载影响。系统不能仅凭单次下载速度判断“节点速度慢”，必须先检查当前出口是否适合测速。第一版建议采用“分时段执行 + 实时负载保护”两层机制：

- 管理员可以配置一个或多个允许测速时段；不在允许时段内的新测速任务保持 `scheduled`，不计为失败。建议默认时段为设备本地时间 `02:00-06:00`，但必须允许修改或关闭。
- 允许时段只代表适合测速，不代表一定空闲；每个节点任务开始前仍必须执行出口负载检查。
- Bagualu 通过 OpenWrt `wan` 网络接口状态和接口字节计数读取出口 `rx_bytes`、`tx_bytes`，在测试前采集至少 5 秒的变化量，分别计算当前下载和上传背景速率。
- 检查必须同时关注上传和下载。上传突发可能造成上行队列或缓冲膨胀，进而影响下载延迟和速度；不能只检查下载方向。
- 如果管理员配置了运营商上行/下行带宽，使用配置带宽计算利用率。任一方向背景利用率超过测速保护阈值时，任务进入 `network_busy` 并等待，不产生节点失败样本。建议默认阈值为任一方向 10%，但阈值必须可配置。
- 测试过程中继续采集 WAN 接口计数，并扣除 Bagualu 当前任务已知的测试流量，估算外部背景流量。外部背景流量超过阈值，或外网基线延迟/丢包明显恶化时，当前速度结果标记为 `network_contended`，不进入速度评分。
- 测试前或测试中无法获取 WAN 接口计数时，不能假设网络空闲；结果标记为 `network_load_unknown`。管理员可以选择暂停测速，默认暂停，避免把未知环境下的结果写入评分。
- `network_busy`、`network_contended`、`network_load_unknown` 都属于基础设施状态，不得降低节点可用率、延迟分、速度分或综合分。
- 单线程队列仍然有效；负载保护只负责等待、暂停或排除样本，不得通过并发测速或额外测速任务探测出口容量。

路由器接口计数只能判断“当前是否有较高背景流量”，不能在不产生额外流量的情况下准确推导运营商的绝对带宽上限。因此系统必须支持配置上行带宽和下行带宽；未配置时只能显示 `capacity_unknown`，不能伪造精确利用率。第一版不自动执行持续占满出口的带宽校准，避免影响家庭网络和其他代理服务。

为降低测试服务器自身限速造成的误判，测速地址必须支持配置多个独立测试源。每个测速批次使用同一个测试源以保证节点之间可比；测试源出现连接失败、响应异常、明显限速或健康检查失败时，暂停该批次并将结果标记为 `speed_source_unavailable`，不计入节点评分。页面必须展示本次测速源和出口负载判定结果。

如未来需要探测出口理论吞吐量，只能提供管理员手动触发的维护模式：明确告警、暂停普通测速、限制最大流量和持续时间、完成后恢复服务，并将校准结果标记为独立的网络容量数据，不直接作为节点速度分。

### 7.5 节点评分机制

每个节点提供三个子评分和一个综合分，分值范围均为 0–100：延迟分、速度分和可用率分。综合分由最近有效测量窗口重新计算，不采用无法从原始数据重放的手工加分或扣分。页面、资源筛选和订阅排序必须使用综合分和推荐状态，不能只依赖单次下载速度。

| 评分 | 主要输入 | 含义 |
| --- | --- | --- |
| 延迟分 | 最近有效协议级请求延迟 | 交互响应能力，延迟越低得分越高。 |
| 速度分 | 最近有效真实下载速度 | 实际下载能力，速度越快得分越高。 |
| 可用率分 | 滚动窗口内有效协议测试成功率 | 长期可用程度，成功率越高得分越高。 |
| 综合分 | 三个子评分的加权调和平均 | 节点当前综合质量，用于排序和推荐过滤。 |

#### 7.5.1 评分输入和有效样本

- 延迟评分只使用经 Mihomo 指定节点代理链路验证的协议级请求延迟，不使用普通 ICMP Ping 代替。默认取最近 20 次有效协议延迟的中位数；Ping 结果独立展示，用于诊断，不直接进入综合分。
- 速度评分使用最近 3 次有效下载测速的中位数，默认最多回看 7 天；单次测速必须经过 Mihomo 指定节点链路验证，并使用实际下载字节数除以有效下载耗时计算。
- 可用率默认统计最近 100 次有效协议级测试，最多回看 7 天；该窗口大小和回看时长可配置。至少需要 20 次有效测试才允许计算可用率分。
- 有效协议测试包括成功和确认由目标节点承载但请求失败的结果；外网基线失败、`network_baseline_unavailable`、`network_baseline_lost`、`network_busy`、`network_contended`、`network_load_unknown`、`speed_source_unavailable`、Mihomo 故障、控制 API 故障、测试站点故障、OpenWrt 资源不足和管理员取消不进入分母。
- 速度评分只使用测速前后出口负载状态为 `clean`、测速源健康且测试链路已由 Mihomo 确认的样本。被背景流量污染或测速源异常的速度结果必须保留用于诊断，但不得进入速度样本窗口。
- 有效样本不足、没有成功延迟样本或没有成功下载测速时，评分状态为 `unrated`，不得显示可用于推荐的综合分。
- 每次评分必须保存输入窗口、样本数量、三个子分、综合分、策略版本和计算时间，保证评分可重放。

#### 7.5.2 子评分归一化

所有归一化结果先限制在 0–100。默认参数可由管理员配置，但修改策略必须产生新版本并重新计算，不得覆盖历史原始测试结果。

延迟分使用最近有效协议级延迟的中位数 `L` 计算：

```text
延迟分 = clamp(100 * (500 - L) / (500 - 50), 0, 100)
```

其中 `L <= 50 ms` 得 100 分，`L >= 500 ms` 得 0 分，中间按线性比例计算。该公式明确保证延迟越低得分越高。

速度分使用最近有效下载速度中位数 `V` 和速度参考值 `Vref` 计算：

```text
速度分 = clamp(100 * V / Vref, 0, 100)
```

`Vref` 默认取当前设备最近 7 天有效测速的第 95 百分位，并允许管理员设置最低参考值和固定目标值。速度越快得分越高；达到参考值后封顶 100，避免单个异常高速样本无限放大分数。

可用率分使用评分窗口内成功协议测试数 `S` 和有效协议测试总数 `N` 计算：

```text
可用率分 = 100 * S / N
```

节点级失败计入 `N`，基础设施错误不计入 `N`。这样外网中断不会导致全部节点同时被判定为不可用。

#### 7.5.3 综合分和推荐规则

默认权重为延迟 30%、速度 30%、可用率 40%。综合分使用加权调和平均：

```text
综合分 = 1 / (0.30 / 延迟分 + 0.30 / 速度分 + 0.40 / 可用率分)
```

计算前必须满足三个子分均存在；任一子分为 0 时综合分为 0。结果四舍五入为整数并限制在 0–100。调和平均会放大低分维度的影响，避免节点仅凭速度很快或延迟很低就掩盖可用率过低的问题。

推荐状态是派生状态，不允许由页面手工覆盖：

| 条件 | 推荐状态 | 外部资源输出 |
| --- | --- | --- |
| 样本不足或状态为 `unrated` | `unrated` | 隐藏 |
| 综合分 `< 60` | `not_recommended` | 隐藏 |
| 综合分 `>= 60` 且最近一次有效协议测试成功 | `recommended` | 可输出 |
| 综合分 `>= 60` 但最近一次有效协议测试失败 | `temporarily_unavailable` | 隐藏，等待下一次成功测试 |

因此，60 分是唯一的默认推荐门槛：综合分达到 60 分或以上才允许推荐；低于 60 分必须在外部订阅和资源 API 中隐藏，但后台仍可查看和继续测试。`unrated`、基础设施暂停和当前不可用节点即使历史综合分达到 60 分，也不能输出。

#### 7.5.4 评分状态

| 状态 | 条件 | 说明 |
| --- | --- | --- |
| `unrated` | 尚未完成首次可信测试 | 不显示虚构分数，不进入按评分自动选择。 |
| `rated` | 三个子评分均有效且满足最小样本数 | 可以计算综合分。 |
| `temporarily_unavailable` | 最近一次有效协议测试失败 | 保留综合分，但暂时不允许输出。 |

节点配置发生连接相关变更时，旧评分归档并重新进入 `unrated`，不得继承旧连接参数的高分。评分策略版本变化时创建重算任务，保留旧评分快照和原始测试结果。

#### 7.5.5 评分可解释性

每次评分重算都保存：测试窗口、测试任务 ID 集合或摘要、有效样本数、三个子分、综合分、策略版本、计算时间和可读原因。不得记录“加分/扣分事件”作为新的业务输入。

页面需要提供“评分时间线”，例如：

```text
综合分 72  延迟 86 | 速度 74 | 可用率 65 | 有效样本 100
综合分 60  延迟 86 | 速度 74 | 可用率 50 | 有效样本 100
暂不可推荐  最近一次协议测试失败，等待下一次有效测试
```

评分规则：

- 评分使用滚动历史样本，不能仅根据一次测试产生可推荐分数。
- 延迟、速度和可用率必须使用同一评分窗口对应的有效样本；不同测量方法不得直接混合。
- 外网基线失败和基础设施错误不得进入可用率分母，也不得降低已有综合分。
- 评分计算必须是确定性的：相同原始测试结果、窗口和策略版本必须产生相同三个子分和综合分。
- 页面展示综合分时必须能展开查看三个子分、样本窗口、基础设施排除数、当前推荐状态和不可用原因。

### 7.6 地区自动分类

- 根据真实出口 IP 的国家/地区代码自动建立地区分类，例如美国、德国、台湾、日本、新加坡和香港。
- 地区分类是系统派生标签，不替代管理员创建的业务分组；一个节点可以同时属于资源分组和一个地区分类。
- 出口归属地变化后自动更新地区分类，并触发相关订阅缓存刷新。
- 未知地区进入“其他/未知”分类，不根据名称强制归入国家组。
- 管理员可以设置地区显示名称、排序和是否包含在订阅输出中，但不能修改节点的原始归属地检测结果。
- 节点列表、分组页面、评分报表和订阅预览都支持按地区筛选。

- 节点总数、可用节点数、异常节点数和禁用节点数。

- 各分组节点数量。
- 最近一次订阅刷新状态。
- 最近一次连通性、Ping 和每日测速任务状态。
- 节点延迟分布。
- 节点下载速度排名或分布。
- 最近失败节点及失败原因。

- 进入“运行后台”的按钮，用于查看当前实时运行情况。

### 8.3 节点列表与详情

节点列表需要支持：

- 分页、搜索和多条件筛选。
- 按延迟、下载速度、最近测试时间和状态排序。
- 按综合分、速度分、延迟分、可用率分、推荐状态和 IP 归属地筛选与排序。
- 批量加入或移出分组。
- 批量启用或禁用测试。
- 手动执行连通性测试、Ping 或下载测速。
- 查看测试任务进度。

节点详情需要展示：

- 节点名称、协议、地址、端口和来源订阅。
- 当前状态和所属分组。
- 最近一次连通性结果。
- 最近一次 Ping 结果。

- 测试历史趋势。
- 失败记录和错误原因。

页面默认隐藏节点密码、UUID、密钥等敏感参数。

### 8.4 运行后台

运行后台用于查看系统当前正在发生的事情，不承担基础配置功能。页面至少包含：

- Bagualu 主程序状态和受管 Mihomo 进程状态。
- 当前 Mihomo 内核及其逻辑测试连接列表，包括内核状态、连接状态、对应节点、启动时间和资源占用。
- 正在执行的订阅刷新、连通性测试、Ping 测试和下载测速任务。
- 当前连接数、活动测试数、实时下载速度和累计测试流量。
- 实时节点列表，可按运行状态、协议、分组和任务筛选。
- 任务失败、核心异常和端口冲突提示。
- 跳转到节点详情、测试详情、流量报表和日志详情的操作入口。

首页和测试中心都需要提供进入运行后台的按钮。运行后台数据支持自动刷新或手动刷新。

### 8.5 流量报表

流量报表用于观察测速产生的流量和节点表现，至少支持：

- 按时间范围查看总测试流量、成功测试流量和失败测试流量。
- 按节点、分组、协议和上游筛选。
- 查看节点下载速度排行、平均速度、最近速度和测速次数。
- 查看每日测速消耗的流量。
- 查看速度、延迟和连通性趋势。
- 导出报表数据。

报表中的测速流量与外部客户端通过资源 API 产生的访问流量分开统计。

### 8.6 日志管理

日志页面至少支持：

- 切换 Bagualu 主程序日志和受管 Mihomo 进程日志。
- 按时间、日志级别、服务、任务 ID、节点 ID 和错误类型筛选。
- 查看实时新增日志。
- 查看核心启动失败、节点连接失败、测速失败和配置错误。
- 下载或清理指定时间范围的日志。

日志页面不得展示完整 API Key、节点密码、UUID、私钥或订阅 URL 中的敏感 token。

### 8.7 管理后台视觉与交互规范

管理后台面向路由器管理员和代理节点运维人员，设计目标是安静、紧凑、清晰、长期查看不疲劳。它是操作后台，不使用营销式首页、巨大标题、装饰性渐变、悬浮卡片墙或无意义动画。

#### 8.7.1 视觉方向

视觉主题命名为“链路控制台”。页面以清晰的网络链路、实时状态和数据表格为主，核心识别元素是“链路证据条”：

```text
Bagualu [运行] -> Mihomo [已连接] -> HK-01 [VLESS] -> 测试目标 [200 OK]
                           连接 128 ms | 42.6 MB/s | 已验证
```

链路证据条出现在运行后台、节点详情和测试结果中，使用统一状态节点展示测试流量确实经过 Mihomo 和指定代理节点。

颜色令牌：

| 名称 | 色值 | 用途 |
| --- | --- | --- |
| Paper | `#F7F8FA` | 页面背景。 |
| Surface | `#FFFFFF` | 工具栏、表格和弹层背景。 |
| Graphite | `#20252B` | 主文字和导航。 |
| Signal Cyan | `#087EA4` | 当前选中、链接和实时链路。 |
| Healthy Green | `#16845B` | 可用、运行、测试成功。 |
| Warning Amber | `#B86A00` | 警告、资源压力和待处理。 |
| Fault Red | `#C43D3D` | 失败、停止和高风险。 |

状态不能只靠颜色表达，必须同时使用图标、文字或形状。深色模式不作为第一版强制要求，但色彩必须通过可访问性对比检查。

字体不依赖互联网字体服务：中文和普通界面使用 OpenWrt 客户端系统无衬线字体栈；端口、IP、流量、速度、时间和日志使用等宽字体栈。标题只用于建立信息层级，不使用超大展示字体。

#### 8.7.2 页面布局

桌面布局：

```text
+--------------+--------------------------------------------------+
| Bagualu      | 顶栏：服务状态 / 核心状态 / 运行后台 / 管理员     |
|              +--------------------------------------------------+
| 仪表盘       | 页面标题 + 筛选/主要操作                          |
| 上游订阅     +--------------------------------------------------+
| 节点         | 摘要指标或链路证据条                              |
| 分组         +--------------------------------------------------+
| 测试中心     | 主表格 / 报表 / 详情                              |
| 流量报表     |                                                  |
| 日志         +--------------------------------------------------+
| 设置         | 分页 / 状态栏                                    |
+--------------+--------------------------------------------------+
```

- 左侧导航固定宽度，按“资源、测试、系统”分区，不把每个功能做成首页卡片。
- 主工作区优先使用工具栏、表格、分栏详情和趋势图；卡片仅用于少量摘要指标或重复实体，圆角不超过 8px。
- 不允许卡片嵌套卡片，不把整个页面区块做成漂浮卡片。
- 表格列宽稳定，状态、延迟、速度和操作列对齐；数据变化不能造成布局跳动。
- 桌面端节点详情可使用右侧抽屉快速查看，完整历史通过独立详情页打开。
- 移动端导航折叠为抽屉，表格保留关键列并提供详情展开，按钮和文字不得重叠或截断。

#### 8.7.3 组件和操作

- 使用图标按钮表示刷新、启动、停止、重启、测速、复制、下载和查看日志；不熟悉的图标提供悬停说明。
- 二元设置使用开关；模式选择使用分段控件；多选使用复选框；端口和队列长度使用数字输入。测速线程数不提供配置项，固定为 1。
- 危险操作使用明确确认框，并写清影响对象；停止 Bagualu 不得暗示会停止 OpenClash。
- 每个异步操作显示排队、运行、成功、失败或取消状态，并提供任务详情入口。
- 空状态说明下一步可执行操作；错误状态给出错误原因和修复入口。
- 自动刷新页面需要显示刷新频率和最后更新时间，并允许暂停，避免实时数据造成持续闪烁。
- 图标和前端资源随安装包本地提供，不依赖公网 CDN。

#### 8.7.4 报表展示

- 仪表盘首先展示可用节点、异常节点、当前任务、实时测速流量和服务健康，不使用装饰性统计数字。
- 趋势图统一使用时间轴，支持查看原始数值和时间；成功率、延迟、速度和流量使用不同语义颜色。
- 节点排行同时显示协议、分组、最近测速时间和结果新鲜度，避免仅按一个速度数字误导排序。
- 所有报表都提供筛选条件摘要、空数据状态和数据更新时间。

#### 8.7.5 视觉验收

- 管理后台在 1440px、1024px、768px 和 390px 宽度下无文字遮挡、按钮溢出和不可操作区域。
- 键盘焦点清晰可见；表单标签、错误提示和状态图标具备可访问名称。
- 首页、节点列表、运行后台、节点详情、流量报表和系统设置保持统一导航、间距和状态语义。
- OpenClash 共存告警必须醒目但不阻断正常查看；只有确认存在启动风险时才禁止启动 Bagualu 核心。
- 页面截图评审必须覆盖正常、空数据、加载、失败、核心停止和 OpenClash 端口冲突状态。

### 10.1 资源接口

| 方法 | 路径 | 作用 |
| --- | --- | --- |

资源接口支持以下参数：

- `format`：输出格式，支持 `json`、`base64`、`clash`、`sing-box`、`dae`、`daed`、`original`；`daed` 是 `dae` 的别名。第一版必须覆盖 Clash Verge、v2rayNG、PassWall、ShadowsocksR Plus+、OpenClash、Clash、Mihomo、Nikki 和 daed，具体映射见 10.2.1。

资源输出默认只包含：节点存在、未被禁用、综合分 `>= 60`、推荐状态为 `recommended`、连通性满足策略且未过期的节点。分组可以提高门槛，但不能降低 60 分门槛，也不能绕过最近一次有效协议测试成功的要求。

### 10.2 输出格式契约

#### 10.2.1 客户端兼容矩阵

Bagualu 按客户端实际可导入的订阅格式生成内容。客户端名称不是输出格式名称；同一输出格式可以被多个客户端使用。第一版必须提供以下兼容关系：

| 客户端 | 第一版输出格式 | 内容要求 |
| --- | --- | --- |
| Clash Verge | `clash` | 完整 Clash/Mihomo YAML，包含 `proxies` 和可用的 `proxy-groups`。 |
| OpenClash | `clash` | 完整 Clash/Mihomo YAML，必须能够通过目标 Mihomo 配置校验。 |
| Clash | `clash` | 完整 Clash YAML；字段以目标 Clash 版本支持范围为准。 |
| Mihomo | `clash` | Mihomo 兼容 YAML，保留协议、TLS、传输层和插件参数。 |
| Nikki | `clash` | Mihomo/Clash 兼容 YAML，不能输出仅适用于其他客户端的字段。 |
| v2rayNG | `base64` | Base64 编码的节点 URI 列表，每行一个节点；保留协议认证、TLS、传输和名称参数。 |
| PassWall | `base64` | Base64 编码的 PassWall 可识别节点 URI 列表；不能返回 Clash YAML 作为默认格式。 |
| ShadowsocksR Plus+ | `base64` | Base64 编码的节点 URI 列表，保留 `ssr://`、`ss://` 及目标版本支持的其他节点 URI。 |
| daed | `dae` 或 `daed` | 返回 daed/dae-wing 可导入的 Base64 节点 URI 订阅，遵守 10.2.4 的纯正文要求。 |

输出格式必须以目标客户端的导入契约为准，不能仅因为节点协议相同就把一种客户端格式标记为另一种格式。无法可靠转换的节点必须跳过，并在预览和生成摘要中给出明确原因；不能生成语法正确但客户端无法导入的伪兼容内容。

第一版不要求为上述客户端分别维护独立的订阅协议。管理员可以为同一资源分组创建多条订阅链接，分别指定 `clash`、`base64` 或 `dae`/`daed`；授权范围、评分门槛、健康过滤、排序和节点数量上限保持一致。

#### Clash/Mihomo 格式

`format=clash` 返回完整可导入的 Clash/Mihomo YAML，而不是只返回节点数组。至少包含：

- `proxies`：通过分组策略筛选后的节点。
- `proxy-groups`：总选择组、综合自动组和动态地区组。
- 必要的基础规则或规则占位策略；是否输出完整 DNS/规则配置由订阅模板决定。

默认生成以下代理组：

```yaml
proxy-groups:
  - name: 节点选择
    type: select
    proxies: [AUTO, 美国节点, 德国节点, 台湾节点, DIRECT]
  - name: AUTO
    type: url-test
    proxies: [筛选后的全部可用节点]
    url: <配置的连通性测试地址>
    interval: <配置的自动测试周期>
  - name: 美国节点
    type: url-test
    proxies: [出口地区为 US 的节点]
  - name: 德国节点
    type: url-test
    proxies: [出口地区为 DE 的节点]
  - name: 台湾节点
    type: url-test
    proxies: [出口地区为 TW 的节点]
```

地区组按实际存在且启用的地区动态生成，不输出空组。组内节点默认按综合评分从高到低排列，并可配置为 `url-test`、`fallback` 或 `select`。节点名称必须唯一、稳定且包含足够的地区/协议识别信息；重名时使用稳定后缀消歧。

#### Base64 节点 URI 格式

`format=base64` 返回 UTF-8 节点 URI 列表的标准 Base64 编码，供 v2rayNG、PassWall 和 ShadowsocksR Plus+ 使用：

1. 每行输出一个完整节点 URI，不输出 JSON、YAML、注释或空的占位节点。
2. 按资源分组、健康状态、最低评分、地区、排序和数量上限过滤后再编码。
3. 节点 URI 必须保留名称、认证、TLS、传输层和协议插件参数。
4. 无法转换为目标 URI 的节点必须跳过，并在预览中记录 `base64_unsupported` 和具体原因。
5. 没有任何兼容节点时返回 `subscription_no_compatible_nodes`，不得返回空 Base64 内容。
6. 响应正文只能包含 Base64 内容，不得混入 JSON 错误信息、BOM 或诊断文本。

v2rayNG、PassWall 和 ShadowsocksR Plus+ 使用同一 `base64` 输出格式时，系统必须根据节点协议生成对应的标准 URI；不能假设三者对所有协议参数的解析行为完全一致。目标客户端不支持的节点要在预览中单独统计。

#### sing-box 格式

`format=sing-box` 返回可导入的 sing-box JSON 配置片段或完整订阅模板，至少包含：

- 节点 `outbounds`。
- 总 `selector` 出站。
- 综合自动 `urltest` 出站。
- 按出口 IP 归属地动态生成的地区 `selector` 或 `urltest` 出站。

无法从 Mihomo 节点字段可靠转换为 sing-box 的节点必须跳过，并在响应摘要或预览接口中返回跳过原因，不得生成无效配置。

#### dae/daed 格式

`format=dae` 和 `format=daed` 返回可以直接作为 daed“导入订阅”URL 使用的响应。两者输出相同，`daed` 作为便于用户识别的别名。

兼容契约依据 dae-wing 的订阅导入行为：daed 将订阅 URL 交给 dae-wing 获取，dae-wing 会先尝试 SIP008，再尝试 Base64 订阅并逐条解析节点分享链接。Bagualu 默认采用兼容范围更广的 Base64 节点链接方式：

1. 从订阅链接绑定的资源分组筛选可用节点。
2. 将节点转换为 dae 当前版本能够解析的标准分享 URI，每行一个节点且必须包含 `://`。
3. 使用 UTF-8 和 LF 换行拼接节点列表。
4. 对完整节点列表进行标准 Base64 编码并作为响应正文返回。
5. daed 用户只需把该 URL 添加为订阅，后续由 daed/dae-wing 定时更新。

专用链接示例：

```text
https://<bagualu-host>/api/v1/subscribe/<token>?format=dae
https://<bagualu-host>/api/v1/subscribe/<token>?format=daed
```

dae/daed 输出要求：

- 仅输出当前目标 dae/dae-wing 版本可识别的协议和字段组合。
- URI 中保留节点名称、协议认证、TLS、传输和插件参数；禁止只输出地址和端口。
- 对不能可靠转换为 dae 分享链接的节点予以跳过，并在预览接口显示 `dae_unsupported` 和具体原因。
- 同一订阅至少有一个兼容节点时才返回成功；没有兼容节点时返回 `subscription_no_compatible_nodes`，不得返回空 Base64 内容。
- 响应正文不得混入 JSON 包装、注释、BOM 或错误提示文本，否则 daed 无法直接导入。
- 响应使用 `text/plain; charset=utf-8`，支持 `ETag` 和最后生成时间响应头。
- 用户代理不是授权依据；daed、dae-wing 或普通客户端请求同一 Token 时得到一致的资源边界。
- dae/daed 格式仍执行分组、健康、最低评分、地区、排序和数量上限策略。

管理后台的订阅链接页面必须提供“复制 daed 订阅链接”操作，并显示兼容节点数、跳过节点数、dae 协议兼容性和最近一次 daed 拉取时间。预览时同时展示 Base64 解码后的 URI 列表，便于排查不兼容节点。

#### Base64 和原格式

- `format=base64` 返回兼容常见客户端的 URI 节点列表再进行 Base64 编码。
- `format=original` 尽可能按节点上游原始协议表达输出，例如原始 URI 行；仅在保存了原始节点片段且节点没有被改变时保证无损。
- 多个上游或多种原始格式混合时，`original` 按节点逐条输出可还原的原始节点；不能安全混合或还原的节点跳过并记录原因。
- 原格式不等同于返回完整上游响应，不能绕过资源分组、评分、健康状态和权限过滤。

### 10.3 订阅响应

- `GET /subscribe/{token}` 以订阅链接绑定的分组作为唯一资源范围。
- 查询参数 `format` 只允许在链接配置的允许格式集合内选择。
- 响应使用正确的 `Content-Type`、文件名、节点数量、生成时间和缓存标识。
- 订阅生成失败时返回结构化错误，不返回部分损坏的 YAML/JSON。
- 相同分组、格式、策略和节点版本可以缓存；节点状态、评分、归属地或分组变化后缓存必须失效。
- 管理后台预览需要显示最终节点数、地区组、排序、跳过节点及原因，避免管理员只能下载后排查。
- 缓存按最终选定格式区分；UA 自动识别完成后使用识别出的格式作为缓存维度，不以完整 UA 字符串无限扩展缓存键。

### 10.4 客户端自动识别

订阅接口支持通过 HTTP `User-Agent`（UA）自动识别客户端并返回适配格式。UA 识别只用于选择输出格式，不参与身份认证、分组授权、评分门槛或节点过滤。

格式选择优先级是强制规则：

1. **请求明确指定 `format`**：直接使用指定格式，完全不读取、不判断 UA。
2. **请求未指定 `format`**：读取 UA 并按客户端识别规则选择格式。
3. **UA 为空、未知或命中规则冲突**：使用订阅链接配置的默认格式。

明确指定格式时的处理规则：

- `format` 值有效且在订阅链接允许格式中：直接生成该格式。
- `format` 不受支持：返回 `unsupported_subscription_format`。
- `format` 受系统支持但不在该链接允许格式中：返回 `subscription_format_forbidden`。
- 明确格式生成失败：返回对应生成错误，不得改用 UA 识别或默认格式重试。

首版 UA 映射：

| UA 关键字示例 | 识别客户端 | 返回格式 |
| --- | --- | --- |
| `ClashVerge`、`Clash Verge`、`Mihomo`、`Clash.Meta`、`Clash`、`OpenClash`、`ClashX`、`ClashForAndroid`、`Nikki` | Clash/Mihomo 系客户端 | `clash` |
| `sing-box`、`SFA`、`SFI`、`SFM` | sing-box 系客户端 | `sing-box` |
| `dae-wing`、`daed`、`dae` | dae/daed | `dae` |
| `v2rayNG`、`v2rayN`、`PassWall`、`ShadowsocksR Plus+`、`Shadowrocket`、`NekoBox` | URI/Base64 订阅客户端 | `base64` |
| 空 UA 或未知客户端 | 未识别 | 链接默认格式 |

识别要求：

- 匹配忽略大小写，并使用有边界的关键字或正则，不能以简单包含关系误判，例如 `dae` 不能误匹配普通单词。
- 规则有明确优先级；更具体的客户端规则先于通用 `Clash`、`dae` 等规则。
- 一次请求命中多个不同格式规则时标记为 `ambiguous`，使用默认格式，不随机选择。
- 内置规则可以随版本更新；管理员可以禁用、调整优先级或增加自定义规则，但不能创建绕过允许格式的映射。
- 请求日志记录识别出的客户端类型、格式、规则 ID 和是否回退，不记录完整订阅 Token；原始 UA 按日志保留策略截断和脱敏。
- 自动识别响应必须添加 `Vary: User-Agent`，防止代理缓存把一种客户端格式返回给另一种客户端。
- 响应头返回 `X-Bagualu-Subscription-Format`、`X-Bagualu-Client` 和 `X-Bagualu-Format-Source`；来源值为 `query`、`user-agent` 或 `default`。
- `X-Bagualu-Format-Source=query` 表示请求明确指定格式，此时客户端识别结果必须为 `not_evaluated`。

示例：

```text
/api/v1/subscribe/<token>?format=dae
  -> 直接返回 dae 格式，不读取 UA

/api/v1/subscribe/<token>
User-Agent: dae-wing/1.x
  -> UA 识别为 dae-wing，返回 dae 格式

/api/v1/subscribe/<token>
User-Agent: unknown-client
  -> 返回该订阅链接的默认格式
```

## 11. 数据关系

```text
上游订阅 1 ---- N 节点
节点     N ---- N 分组
节点     1 ---- N 测试结果
节点     1 ---- N 评分快照
节点     N ---- 1 当前出口地区
API Key  N ---- 1 默认分组
订阅链接 N ---- 1 资源分组
后台任务 关联 上游刷新 / 节点测试 / 数据维护
```

系统需要保存节点来源关系，使管理员可以回答：

- 节点来自哪个订阅。
- 节点属于哪些分组。
- 节点最近一次测试是什么结果。
- 节点当前综合分及三个子分如何计算，且综合分低于 60 时不会进入外部资源。
- 节点真实出口 IP 属于哪个国家/地区，数据何时更新。
- 节点为什么被排除出资源输出。

## 12. OpenWrt 页面与服务验收标准

### 12.1 服务验收

- 能在 OpenWrt 上安装并注册服务。
- 路由器重启后服务可以按配置自动启动。
- 可以通过 OpenWrt 服务命令启动、停止、重启和查看状态。
- 服务异常退出后可以自动恢复。
- LuCI 可以统一启用、禁用、启动、停止和重启 Bagualu 主服务，并分别展示 Bagualu 与内部 Mihomo 的状态和诊断信息。
- LuCI 的主服务启用开关持久化到独立 UCI 配置，并通过 ubus/procd 控制 Bagualu 主程序生命周期；Mihomo 生命周期由 Bagualu 管理。
- 启用后 procd 必须启动 Bagualu，Bagualu 再完成 Mihomo 启动、端口和控制 API 检查；任一检查失败时 LuCI 必须显示 `failed`、错误码、失败阶段和最近错误摘要。
- Bagualu 主程序由 procd 自动拉起，Mihomo 由 Bagualu 自动拉起；达到各自崩溃阈值后必须停止重启并告警。
- 禁用后不得因 procd 或 Bagualu 内部监督机制自动拉起 Bagualu 或 Mihomo。
- 启动、停止和重启操作必须通过异步操作 ID 查询结果，不能依赖被停止服务的 HTTP 响应完成操作确认。
- 管理员可以在页面修改管理员账号、密码、管理端口、Mihomo 控制端口和本地测速代理端口。
- Bagualu 与 OpenClash 同时运行时，OpenClash 代理、DNS、规则、控制 API 和现有连接不受影响。
- Bagualu 启动、停止、升级和卸载前后，系统防火墙、路由、DNS 和 OpenClash 配置保持不变。
- 端口冲突只阻止 Bagualu 核心启动或触发自身端口重分配，不停止其他服务。
- 在不依赖 Docker 的情况下完成核心功能。
- 在有限内存和存储条件下限制测速队列长度、单次流量及历史数据；测速执行固定为单线程。

### 12.2 页面验收

- 管理员可以登录页面并看到首页统计。
- 可以创建上游并手动刷新，页面显示刷新结果。
- 可以查看节点列表、节点详情和节点来源。
- 可以创建分组并调整节点归属。
- 可以看到连通性、Ping、下载速度三类测试结果，以及测速时段、WAN 上下行背景速率、出口负载状态和测速源状态。
- 节点测试确实通过 Bagualu 管理的 Mihomo 内核依赖进程完成，而不是由页面或普通 HTTP 请求模拟。
- 页面可以查看受管 Mihomo 进程状态、版本和测试任务占用情况，但没有独立的 Mihomo 服务启用开关。
- 页面可以查看协议能力矩阵，以及每种协议无法解析、加载或测试的具体原因。
- LuCI 页面可以运行共存检查，并通过按钮打开独立管理后台。
- 可以看到节点测试历史和失败原因。
- 可以通过按钮进入运行后台，查看 Bagualu 管理的 Mihomo 内核、逻辑测试连接、任务、连接数、实时速度和流量。
- 可以查看节点列表、流量报表、速度排行和历史趋势。
- 可以查看并筛选 Bagualu 主程序和受管 Mihomo 进程日志。
- 可以创建 API Key 并在页面中看到资源访问地址。
- 可以创建绑定资源分组的订阅链接，选择 Clash Verge、OpenClash、Clash、Mihomo、Nikki 使用的 Clash/Mihomo YAML，或选择 v2rayNG、PassWall、ShadowsocksR Plus+ 使用的 Base64 URI，以及 daed 专用格式，并预览最终结果。
- 订阅预览必须按目标客户端显示兼容节点数、跳过节点数和每个跳过原因；不能把仅支持某一客户端的输出标记为所有客户端通用。
- 可以直接复制 daed 专用订阅链接并导入 daed，页面显示兼容节点和跳过原因。
- 订阅链接页面可以输入或选择客户端 UA，预览识别出的客户端、最终格式、命中规则和回退原因。
- 节点页面可以查看真实出口 IP、地区分类、综合分和速度/延迟/可用率三个子评分。
- 节点评分详情可以查看评分窗口、有效样本、三项归一化输入、权重、策略版本和推荐状态变化。
- 测试任务在出口繁忙、负载未知、测速源异常或不在允许时段时，页面必须显示等待/排除原因，不能显示为节点失败。
- Clash/Mihomo 订阅预览可以看到 AUTO 和美国、德国、台湾等实际存在的动态地区组。
- 页面在 OpenWrt 常见桌面浏览器和移动浏览器上可用。

### 12.3 API 验收

- 管理 API 支持页面完成所有管理操作。
- 节点测试 API 确实按节点协议执行测试。
- 节点测试 API 能够驱动 Bagualu 管理的 Mihomo 内核依赖进程，并将内核连接和流量结果转换为统一测试结果。
- 任意时刻只能有一个节点测试任务处于执行状态；同时提交多个测试任务时必须进入同一个队列，禁止并发测速，且测试结果必须能够证明任务执行顺序。
- 测试任务必须记录开始前和结束后的 WAN 上下行计数、背景速率、配置带宽、负载状态、测速时段和测速源；出口繁忙、负载未知或测速源异常的结果不得进入速度评分。
- 停止 Mihomo 后发起节点测试，任务必须返回 `core_unavailable`，不得产生成功结果。
- 阻断 Mihomo 控制 API 后发起节点测试，任务必须返回 `core_api_unavailable`。
- 测试结果必须能够提供 Mihomo PID、指定节点逻辑连接、节点链路和流量差值证据。
- 测试请求无法确认经过指定节点时，必须返回 `core_route_unverified`，不得回退直连。
- 共存测试必须覆盖 OpenClash 正在运行时安装、启动、测速、停止、升级和卸载 Bagualu 的完整流程。
- 协议测试必须基于目标 Mihomo 版本的能力矩阵逐项执行配置加载和真实连通性测试。
- 系统能够通过运行后台接口展示受管 Mihomo 进程返回的实时运行数据。
- 外部客户端使用 API Key 可以获取授权分组资源。
- 未授权客户端不能获取其他分组资源。
- 上游刷新失败不会清空上一次有效节点资源。
- 同一入口 IP 的节点共享网络层不可达时，系统必须统一暂停测试和隐藏输出；单个协议握手或认证失败不得错误隐藏同 IP 的其他协议节点。
- 相同入口 IP+端口但不同协议的节点必须分别保存速度和评分，不能复制代表节点速度；代表节点预检查只能用于调度优化。
- 订阅链接只能返回其绑定资源分组中的节点，查询参数不能越权访问其他分组。
- 生成的 Clash Verge、OpenClash、Clash、Mihomo 和 Nikki 订阅必须通过目标 Mihomo/Clash 配置校验，并包含有效 `proxies` 和 `proxy-groups`。
- v2rayNG、PassWall 和 ShadowsocksR Plus+ 订阅必须返回可导入的标准 Base64 URI 列表；每个目标客户端的协议转换失败必须提供 `base64_unsupported` 原因。
- 生成的 sing-box JSON 必须通过对应配置结构校验，无法转换的节点必须提供跳过原因。
- dae/daed 订阅必须能够被目标 dae-wing 版本直接导入，并解析出与预览一致的节点数量。
- dae/daed 响应必须是纯 Base64 节点 URI 列表，不得包含 JSON 包装、BOM 或诊断文本。
- dae 不支持的节点必须标记 `dae_unsupported` 并从输出中跳过，不能生成看似成功但无法连接的链接。
- 地区自动组必须来自节点真实代理出口 IP 归属地，不能只依赖节点名称或服务器域名 IP。
- 评分验收覆盖延迟分、速度分、可用率分、调和平均综合分、权重、样本不足、基础设施排除、60 分推荐门槛和评分重算。
- 相同原始测试结果、评分窗口和策略版本重复计算必须得到相同结果，批量重算必须幂等。
- 延迟降低、速度提升、可用率提升必须使对应子分不降低；任一维度显著下降必须使综合分下降或进入不可推荐状态。
- Mihomo、测试站点、OpenWrt 资源或任务取消等基础设施故障不得错误扣除节点分数。
- 突发上传或其他外部流量导致 WAN 出口繁忙时，系统必须暂停或排除当前测速样本，不得把出口拥塞误判为节点速度低。
- 未配置运营商带宽或无法读取 WAN 接口计数时，系统必须显示容量未知或负载未知，不得生成伪造的出口利用率。
- 同一原始测试结果、评分窗口、评分版本和策略必须产生相同分数，评分结果可以从评分快照和原始结果完整重放。
- `original` 输出仍受分组、健康和评分策略过滤，不得直接泄露完整上游订阅。
- 请求显式指定 `format` 时必须返回该格式且标记 `X-Bagualu-Format-Source: query`，不执行 UA 识别。
- 请求没有 `format` 时必须按 UA 识别；已知 Clash、sing-box、dae/daed 和 Base64 客户端分别返回映射格式。
- UA 未知或冲突时必须使用链接默认格式，并通过响应头说明来源为 `default`。
- 自动识别响应必须包含 `Vary: User-Agent`；不同 UA 通过共享缓存访问时不得收到其他客户端格式。
- UA 伪造不能改变 Token 绑定分组、允许格式、最低评分和节点过滤结果。

## 13. 代码架构与工程约束

本节是后续实现的强制约束。AI 大模型或开发人员编写代码时必须遵守；不得为了快速完成单个功能破坏模块边界、复制业务规则或将多个职责堆入同一文件。

### 13.1 架构原则

- 采用清晰的分层架构和依赖倒置，业务规则不直接依赖 HTTP 框架、数据库驱动、Mihomo 私有格式、OpenWrt 命令或 LuCI 实现。
- 单一职责：一个模块只承担一个明确变化原因，例如订阅解析、节点归组、测速编排、Mihomo 调用、任务存储分别维护。
- 高内聚、低耦合：同一业务能力放在同一模块，对外只暴露必要接口。
- 组合优于继承；只在存在多个真实实现或明确测试边界时增加接口和抽象。
- 复用业务能力，不复制业务规则。页面 API、定时任务和手动任务必须调用相同的应用服务。
- 禁止以 `utils`、`helpers`、`common` 等目录长期堆放无归属逻辑；通用代码必须有明确领域或基础设施归属。
- 架构允许未来替换存储、Web 框架或 Mihomo 版本，但第一版不实现可选内核和多内核并行管理，也不为没有明确需求的场景提前设计复杂插件系统。

### 13.2 分层与依赖方向

```text
入口层（HTTP / CLI / 定时器 / LuCI RPC）
                    |
                    v
应用层（用例编排 / 事务 / 权限 / 任务协调）
                    |
                    v
领域层（实体 / 值对象 / 规则 / 接口契约）
                    ^
                    |
基础设施层（数据库 / Mihomo / OpenWrt / 日志 / 文件系统）
```

依赖规则：

- 入口层可以依赖应用层，不得绕过应用层直接操作数据库或 Mihomo。
- 应用层可以依赖领域层定义的接口，不得依赖具体数据库表、Mihomo YAML 字段或 shell 命令细节。
- 领域层不得依赖入口层、基础设施层、Web 框架、ORM 或操作系统。
- 基础设施层实现领域层或应用层定义的端口接口，负责所有外部系统细节。
- 前端只能通过版本化 API 使用后端能力，不直接读取数据库文件、UCI 文件或 Mihomo 配置。
- LuCI 页面只调用受控 RPC/HTTP 接口，不直接拼接 shell 命令执行服务操作。

### 13.3 后端模块边界

后端至少按以下业务模块组织：

| 模块 | 职责 | 禁止承担 |
| --- | --- | --- |
| `auth` | 管理员认证、会话、密码修改。 | 节点或系统服务管理。 |
| `upstream` | 上游 CRUD、刷新编排、刷新记录。 | 直接执行节点测速。 |
| `subscription` | 格式识别、订阅解析、节点标准化。 | 数据持久化和 HTTP 响应。 |
| `node` | 节点查询、状态、来源和管理属性。 | Mihomo 进程控制。 |
| `group` | 分组、节点归属和输出策略。 | API Key 鉴权实现。 |
| `measurement` | 连通性、Ping、测速任务编排和结果计算；只依赖领域定义的内核端口接口。 | Mihomo HTTP 路径、JSON、认证和进程命令。 |
| `scoring` | 延迟、速度、可用率三个子评分、综合分、推荐状态、评分策略和重算。 | 执行网络测试或修改节点。 |
| `geolocation` | 真实出口 IP 归属地查询、缓存和地区分类。 | 根据名称伪造归属地。 |
| `core` | Bagualu 内部的内核能力端口、能力矩阵和内核证据模型，不包含 Mihomo HTTP 实现。 | 页面或数据库框架代码、Mihomo 私有协议实现。 |
| `mihomo` | Mihomo 配置生成、子进程启动/停止/重启、HTTP 控制 API 客户端、代理端口客户端和状态读取。 | LuCI/procd 服务控制、业务分组和资源授权规则。 |
| `openwrt` | procd/UCI/ubus/LuCI 集成、Bagualu 主服务生命周期、共存检测和系统状态。 | Mihomo 业务进程管理、节点解析和测速计算。 |
| `resource` | API Key 授权、分组资源筛选和订阅输出。 | 修改上游或节点。 |
| `subscription_output` | Clash、sing-box、dae/daed、Base64、原格式渲染与模板校验。 | 决定分组授权和节点评分。 |
| `client_detection` | User-Agent 规则、格式选择优先级、冲突识别和默认回退。 | 身份认证、分组授权和节点筛选。 |
| `job` | 单线程测试队列、取消、重试和任务状态。 | 具体业务规则。 |
| `report` | 统计查询、趋势和导出。 | 修改原始测试结果。 |
| `audit` | 操作审计和敏感信息脱敏。 | 执行业务操作。 |

跨模块调用通过公开应用服务或明确接口完成，不得直接访问其他模块内部 repository、未导出类型或私有数据结构。

### 13.4 前端模块边界

- 页面按业务路由拆分：仪表盘、上游、节点、分组、测试、运行后台、报表、日志和设置。
- 页面组件负责组合和交互，不在组件内实现 API 权限、测速规则或数据聚合算法。
- API 客户端、查询状态、表单校验、图表数据转换和展示组件分别组织。
- 可复用组件必须来自至少两个真实使用场景；只用于单一页面的组件保留在页面模块内部。
- 全局状态只保存跨路由且确有共享需求的数据，例如管理员会话和系统运行摘要；筛选、分页和弹窗状态保留在页面内。
- 状态文案、状态颜色、时间、速度和流量格式化使用集中定义，避免各页面出现不同语义。
- LuCI 设置页与独立管理后台可以使用不同构建入口，但共享 API 契约和状态定义，不复制后端业务逻辑。

### 13.5 参考项目结构

实际语言和框架确定后可以调整目录名称，但职责和依赖方向必须保持：

### 13.6 文件规模与代码拆分

- 手写源码单文件硬性上限为 **1000 行**，目标控制在 **500 行以内**。
- 文件达到 500 行时，代码评审必须检查是否存在职责过多；达到 800 行时必须制定拆分方案；不得合入超过 1000 行的手写源码。
- 自动生成代码、协议生成文件、数据库迁移和第三方代码可以超过 1000 行，但必须放在明确的 `generated`、`migrations` 或 `vendor` 边界中，禁止手工混入业务逻辑。
- 单个函数应完成一个任务。出现多级流程、多个外部依赖或大量分支时，拆成可命名、可测试的步骤。
- 一个文件不同时包含 HTTP 路由、业务规则、数据库查询和系统命令调用。
- 不通过压缩格式、超长行或把代码塞入大字符串规避文件行数约束。
- 拆分依据是职责和变化原因，不以机械方式将一个大文件切成无语义的 `part1`、`part2`。

### 13.7 接口、模型与错误

- HTTP 请求/响应 DTO、领域模型、数据库模型和 Mihomo 配置模型分离，转换在模块边界完成。
- API 契约集中维护并版本化；前后端不得各自手写一套含义不同的状态枚举。
- 接口应小而明确，由使用方定义；禁止创建包含大量无关方法的万能 Service 或 Repository。
- 领域错误使用稳定错误码，例如 `core_unavailable`、`node_load_failed`，入口层负责转换为 HTTP 状态和用户可读信息。
- 外部错误必须保留原因链和上下文，但日志不得泄露管理员密码、API Key 或节点敏感参数。
- 时间统一保存为 UTC，API 使用标准时间格式，页面按用户时区展示。
- 速度、流量、延迟和比例使用明确单位，禁止以无单位数字在模块间传递。

### 13.8 Mihomo 与 OpenWrt 隔离

- `measurement` 模块只依赖领域定义的核心接口，不允许直接调用 Mihomo HTTP API、解析 Mihomo JSON 或执行 Mihomo 命令。
- 所有 Mihomo 私有配置、进程信号、子进程生命周期、API 路径和代理端口适配集中在 `infrastructure/mihomo`；该模块由 Bagualu 应用层调用，不直接接触 LuCI/procd。
- 所有 UCI、ubus、procd、Bagualu 主服务启动/停止/重启、文件路径、进程查询和端口检测集中在 `infrastructure/openwrt`。
- Mihomo 适配器和 OpenWrt 适配器都必须可由测试替身替换，业务测试不得要求真实路由器或真实核心。
- 真实 Mihomo/OpenWrt 测试放入独立集成测试和系统验收测试，不与快速单元测试混合。
- 共存检查独立于修复动作；检测模块只能报告风险，只有 Bagualu 自身配置允许由管理用例修改。

### 13.9 测试与质量门禁

- 领域规则和应用服务必须有单元测试，覆盖成功、失败、超时、取消和重复执行。
- Mihomo 适配器使用契约测试，验证配置生成、API 响应转换、错误映射和进程回收。
- HTTP API 使用集成测试验证认证、权限、参数、错误码和响应模型。
- 前端关键页面覆盖组件测试；上游添加、节点测速、分组授权和打开运行后台覆盖端到端测试。
- OpenClash 共存、Mihomo 真实链路、安装升级和卸载使用 OpenWrt 环境验收测试。
- 每次合入必须通过格式化、静态检查、单元测试、架构依赖检查、单文件行数检查和敏感信息扫描。
- 测试不得依赖执行顺序、固定端口、公网稳定性或开发者机器上的 OpenClash 配置。
- 修复缺陷必须增加能够复现该缺陷的测试，除非评审记录明确说明无法自动化的原因。

### 13.10 可读性与文档

- 命名使用业务语言，保持上游、节点、分组、测试任务、受管 Mihomo 进程等术语在代码、API 和页面中一致。
- 避免无意义缩写、单字母变量和含糊名称，例如 `data`、`manager`、`handleAll`。
- 注释解释约束、原因和非显然取舍，不复述代码行为；复杂链路在入口处提供简短说明。
- 对外模块、公共接口、错误码、配置项和 API 必须有文档。
- 重要架构决策使用 ADR 记录，包括技术栈、存储、Mihomo 调用模式和 OpenWrt 打包方式。
- SDD 是需求和架构基线；实现与 SDD 不一致时，必须先更新文档并评审，不允许代码静默偏离。

### 13.11 架构验收标准

- 从 HTTP 路由可以清晰追踪到应用用例、领域接口和基础设施实现，没有跨层捷径。
- 手动触发测试和定时测试复用同一测量应用服务，结果计算只有一份实现。
- 更换 Mihomo 测试替身不需要修改测量业务规则；更换存储实现不需要修改 HTTP 路由。
- LuCI 和独立管理后台通过相同后端契约完成服务控制，不包含两套启停逻辑。
- 仓库不存在超过 1000 行的手写源码文件；超过 500 行的文件有明确保留理由或拆分记录。
- 模块依赖检查没有循环依赖，领域层不依赖基础设施层。
- 新增协议只需要扩展订阅解析/统一节点模型和 Mihomo 配置转换，不需要修改分组、报表和 API Key 模块。
- 新增订阅输出格式只需增加格式渲染器和契约测试，不修改分组授权、评分和地区识别模块。
- 新增客户端 UA 规则只修改 `client_detection` 映射和测试，不修改各格式渲染器。
- 调整动态评分策略不修改测试原始数据和订阅渲染器；订阅渲染器只消费已确定的排序结果。
- 新增页面不要求复制 API 客户端、状态颜色、单位格式化或权限逻辑。
