# Bagualu 代理池服务 SDD

状态：Draft

## 1. 文档说明

本文档用于指导 AI 大模型或开发人员实现 Bagualu 代理池项目。本文档只定义产品需求、系统边界、模块架构、页面、接口和验收标准，不提前限定具体编程语言、数据库 ORM 或前端组件库。

在需求确认完成前，只维护本文档，不开始编写业务代码。

## 2. 项目目标

Bagualu 是一个运行在 OpenWrt 路由器上的代理池管理服务，主要能力是：

1. 收集多个代理订阅作为上游。
2. 解析订阅中的代理节点并统一管理。
3. 通过分组组织节点资源。
4. 对节点进行真实的连通性、延迟和下载速度测试。
5. 通过可视化页面查看上游、节点、分组和测试结果。
6. 通过 API Key 获取指定分组的代理订阅资源。

系统不做代理转发。系统自身只负责订阅收集、节点管理、节点测试、结果展示和资源输出。

## 3. 角色

### 3.1 管理员

管理员通过 Web 页面管理系统，可以：

- 管理订阅上游。
- 查看和管理节点。
- 创建和维护分组。
- 配置节点测试策略。
- 查看节点连通性、延迟和下载速度。
- 管理 API Key。
- 查看任务执行记录和系统状态。

### 3.2 API 使用者

API 使用者不需要进入管理页面，通过 API Key 获取被授权分组的订阅资源。

### 4.1 模块说明

| 模块 | 作用 |
| --- | --- |
| Web 管理页面 | 提供系统配置、节点管理、分组管理、测试结果和任务状态的可视化操作。 |
| HTTP API 服务 | 为页面、外部客户端和 OpenWrt 服务提供统一接口。 |
| 定时任务服务 | 按计划执行订阅刷新、节点测试和历史数据清理。 |
| 测速核心适配层 | 将节点配置和测速参数转换为测速核心可执行的配置，管理核心实例，并读取连接状态和流量结果。 |
| 测速核心服务 | 独立运行的多协议核心，负责实际协议连接、握手、测试请求和流量统计。Bagualu 不在业务层重复实现协议。 |
| 数据存储 | 保存上游、节点、分组、测试结果、任务和 API Key。 |
| OpenWrt 服务封装 | 负责开机启动、停止、重启、配置加载和日志输出。 |

### 4.2 运行形态

系统必须支持以下两种运行形态：

- **单体管理模式**：Web 页面、HTTP API、定时任务和管理逻辑运行在 Bagualu 服务中，适合资源有限的路由器。
- **核心服务模式**：测速核心以独立进程运行，由 Bagualu 管理和调用，适合节点较多或测速任务较重的设备。

第一版必须保留 Bagualu 服务与测速核心服务的进程边界。两者可以在同一 OpenWrt 设备运行，但测速核心不能只作为页面内的临时模拟逻辑。

### 4.3 测速核心服务联动

测速核心服务是节点测试和真实测速的基础组件。Bagualu 主程序不直接实现所有代理协议，而是通过 Mihomo 适配层直接管理 Mihomo 进程和调用其控制 API。

联动关系如下：

```text
节点配置 + 测试参数
        |
        v
Bagualu 任务服务
        |
        v
测速核心适配层
        |
        +--> 创建/更新临时核心配置
        +--> 启动或复用核心实例
        +--> 获取本地代理入口
        +--> 发起测试请求
        +--> 读取连接状态、字节数和耗时
        +--> 停止测试实例并回收资源
        |
        v
测速核心服务
        |
        v
节点真实出口
```

第一版不额外开发一套独立的“测速核心业务服务”。Bagualu 直接调用 Mihomo，调用边界如下：

- **进程调用**：Bagualu 生成独立配置，通过命令行启动、停止和监控 Mihomo 子进程。
- **控制 API 调用**：Bagualu 通过 Mihomo `external-controller` 接口读取版本、代理、连接、流量、日志和延迟信息，并执行必要的配置重载或节点选择。
- **代理端口调用**：Bagualu 的连通性请求和下载测速程序连接 Mihomo 暴露的本地 HTTP/SOCKS/Mixed 端口，确保测试流量经过指定节点。
- **结果计算**：Mihomo 提供连接链路和流量数据；Bagualu 使用实际下载字节数与有效耗时计算最终速度并保存结果。

不采用把 Mihomo 源码嵌入 Bagualu 进程的方式。Mihomo 没有作为项目稳定契约的嵌入式 SDK，直接源码耦合会增加 OpenWrt 编译、升级和崩溃隔离成本。

测速核心服务需要满足以下要求：

- 采用成熟、协议覆盖范围广的代理核心，覆盖项目确认范围内的节点协议。
- 支持由 Bagualu 通过进程参数、配置文件、控制 API 和本地代理端口直接调用。
- 支持多个测试实例隔离运行，并返回任务状态和流量统计。
- 支持查看核心版本、支持协议、运行实例、连接数和资源占用。
- 支持在 OpenWrt 上独立启动、停止、重启和查看状态。

第一版测速核心确定采用 **Mihomo（原 Clash.Meta）**。不采用已经停止维护的旧版 Clash 核心。Mihomo 负责节点协议连接、代理转发、连接信息和流量统计，Bagualu 负责订阅、任务调度、测速计算、结果保存和页面展示。

OpenClash 是 OpenWrt 上的 LuCI 管理插件，不是代理核心本身。OpenClash 通常管理 Mihomo/Clash 系列核心，因此 Bagualu 与 OpenClash 可以使用同一核心家族和相近配置格式，但两者不是同一个服务。

Bagualu 不得直接接管或重载 OpenClash 正在运行的核心实例。默认部署方式为：

- Bagualu 携带或安装自己兼容架构的 Mihomo 可执行文件。
- Bagualu 默认使用自身独立路径下的 Mihomo 二进制，不覆盖、不替换、不升级 OpenClash 的核心文件。
- Bagualu 使用独立的 Mihomo 进程、配置目录、控制端口和本地代理端口。
- Mihomo 控制 API 和测速代理端口默认只监听 `127.0.0.1`，控制 API 使用独立密钥，仅允许 Bagualu 调用。
- Bagualu 测速实例不修改 OpenClash 配置，不停止 OpenClash，不占用 OpenClash 端口。
- 当 OpenClash 与 Bagualu 同时运行时，页面必须检测并提示端口冲突和内存占用风险。
- 后续可以增加“只读复用系统 Mihomo 二进制”的安装选项，但仍使用 Bagualu 自己的独立进程和配置；Bagualu 不得通过该选项修改或升级被复用文件。

#### 4.3.1 与 OpenClash 共存的硬性约束

Bagualu 安装和运行后不得改变 OpenClash、PassWall、HomeProxy 等现有代理服务的配置、进程、网络规则和流量路径。第一版测速采用“本地显式代理”模式，不使用透明代理模式。

- 使用独立的 OpenWrt 服务名、进程 PID 文件、配置目录、数据目录、日志标识和临时目录。
- Mihomo 控制 API、Mixed/HTTP/SOCKS 测速入口只监听 `127.0.0.1`，不得监听 LAN 或 WAN 地址。
- 安装时动态检查端口占用；默认端口冲突时自动分配可用端口并保存配置，不得停止占用端口的其他服务。
- 不启用 Mihomo TUN、Redir、TProxy、Fake-IP DNS、系统代理或 LAN 访问能力。
- 不写入或修改 nftables、iptables、ip rule、ip route、dnsmasq、DHCP、默认路由和 DNS 配置。
- 不读取、覆盖、重载或删除 OpenClash 的运行配置与订阅数据。
- 不向 OpenClash 控制 API 发送修改、切换节点、重载或停止指令。
- Bagualu 停止或卸载后，只清理自身进程、配置和临时资源，不影响 OpenClash 当前连接。
- 同时运行时限制 Mihomo 实例数、测试并发、内存和测速流量；达到设备资源门槛后暂停新任务并在页面告警。

启动前必须执行共存检查：服务名、进程、控制端口、代理端口、配置目录、可用内存和 OpenClash 状态。检查发现风险时，只阻止 Bagualu 测速核心启动，不得对其他服务采取修复动作。

卸载验收必须确认：OpenClash 服务状态未变化，OpenClash 配置文件未变化，系统防火墙、路由和 DNS 未被 Bagualu 修改。

#### 4.3.2 全协议支持定义

“支持全协议”定义为：覆盖当前安装的 Mihomo 版本所支持的全部节点协议、传输方式和协议参数，而不是承诺支持世界上所有代理协议。

- 系统启动时读取 Mihomo 版本，并形成对应的协议能力清单。
- 订阅解析器必须完整保留 Mihomo 节点字段，不能只提取地址、端口等基础字段。
- Clash/Mihomo YAML 节点优先使用结构化解析和字段透传，保持协议、TLS、传输层和插件参数。
- URI/Base64 订阅转换为统一节点模型后，再由 Mihomo 适配器生成核心配置。
- 第一版协议范围至少覆盖 Mihomo 当前支持的主流协议，包括 SS、SSR、VMess、VLESS、Trojan、HTTP、SOCKS5、Snell、WireGuard、Hysteria/Hysteria2、TUIC、SSH 以及 Mihomo 后续兼容协议。
- 每种协议都必须通过“配置加载测试 + 协议级连通性测试”后才能标记为已支持。
- Mihomo 支持但 Bagualu 暂未解析的节点标记为 `parser_unsupported`；Mihomo 本身不支持的节点标记为 `core_unsupported`。
- 不支持的节点可以保留并展示原始来源与原因，但不得进入测速成功结果或可用资源输出。

管理后台需要展示当前 Mihomo 版本的协议能力矩阵，包括：可解析、可加载、可连通测试、可下载测速及失败原因。Mihomo 升级后应自动重新检测能力，不在代码中固定一份永久不变的协议列表。

测速核心适配层至少需要提供以下能力：

- 将统一节点配置转换为测速核心配置。
- 按节点或测试任务创建隔离的临时连接实例。
- 启动、停止、重启和检查核心实例状态。
- 为测试任务提供本地代理入口。
- 把连通性测试和下载测速请求导向指定节点。
- 获取实际连接状态、请求耗时、下载字节数和错误信息。
- 测试完成后释放端口、进程、临时配置和临时文件。

测速核心适配层第一版实现 Mihomo 进程管理器、配置生成器和控制 API 客户端。模块边界仍然保留，上层页面、任务 API、测试结果和资源 API 不直接依赖 Mihomo 私有配置格式，以便未来增加其他核心。

### 4.4 内核直调测试契约

所有协议级连通性测试和实际下载测速都必须经过 Bagualu 管理的 Mihomo 实例。该要求属于硬性系统契约，不允许在实现中回退成系统直连、仅测试目标端口或使用其他网络出口。

每次测试必须执行以下链路：

1. Bagualu 校验节点协议和必要参数，并生成本次测试专用的 Mihomo 配置。
2. Bagualu 调用 Mihomo 配置检查能力；配置无效时任务直接失败。
3. Bagualu 启动或复用受管 Mihomo 实例，记录进程 ID、控制 API 地址、代理端口和配置版本。
4. Bagualu 调用控制 API 完成启动握手，确认 Mihomo 版本、API 鉴权和节点已加载。
5. Bagualu 将本次任务绑定到唯一节点，并记录测试前的连接数和流量计数。
6. 测试程序只允许连接本次 Mihomo 实例的本地代理端口，通过该端口发起连通性请求或下载请求。
7. Bagualu 从 Mihomo 控制 API 查询该任务对应的连接链路、节点名称和流量变化，并校验实际出口。
8. 只有“测试请求成功、指定节点链路可确认、Mihomo 流量增加”同时成立时，测试才允许标记为成功。
9. Bagualu 保存结果和内核证据摘要，随后关闭连接并回收临时实例、端口和配置。

失败规则：

- Mihomo 可执行文件不存在、无法启动或异常退出：任务失败，错误为 `core_unavailable`。
- 控制 API 不可访问或鉴权失败：任务失败，错误为 `core_api_unavailable`。
- 节点未被 Mihomo 正确加载：任务失败，错误为 `node_load_failed`。
- 测试请求未经过指定节点、无法确认连接链路或内核流量没有变化：任务失败，错误为 `core_route_unverified`。
- 代理请求失败或超时：按连接阶段记录失败，不得改用 OpenWrt 默认出口重试。

每条成功测试结果必须保存以下内核证据摘要：Mihomo 版本、受管实例 ID、配置摘要、目标节点 ID、Mihomo 中的节点名称、连接 ID、出口地址、测试前后流量差值和测试时间。敏感节点参数不得写入证据摘要或普通日志。

## 5. OpenWrt 服务需求

### 5.1 服务要求

系统必须以 OpenWrt 服务形式安装和运行，不能只提供 Docker 或普通开发机启动方式。

服务需要支持：

- 安装后注册为 OpenWrt init 服务。
- 开机自动启动。
- `start`、`stop`、`restart`、`reload`、`status` 操作。
- 异常退出后自动拉起。
- Bagualu 管理服务和测速核心服务可以分别启用、禁用、启动、停止和重启。
- 管理服务和测速核心服务使用独立端口，端口冲突时页面必须提示。
- 使用 OpenWrt 配置目录保存配置和数据。
- 使用 OpenWrt 日志机制输出运行日志。
- 支持配置管理页面监听地址、管理端口、测速核心服务端口、数据目录、管理员认证和任务开关。
- 在低内存设备上限制并发测试数量和历史数据量。

### 5.2 OpenWrt LuCI 配置页面

安装包必须在 OpenWrt LuCI 中注册独立菜单入口。LuCI 页面保持轻量，只负责服务安装后的基础控制和诊断；节点管理、报表等复杂功能进入 Bagualu 独立管理后台。

LuCI 页面提供以下运行配置：


| 配置项 | 说明 |
| --- | --- |
| 服务状态 | 显示运行、停止或异常状态。 |
| 管理服务状态 | 显示 Bagualu 管理服务是否启用和运行。 |
| 测速核心状态 | 显示测速核心是否启用、运行、异常或未安装。 |
| Mihomo 信息 | 显示 Mihomo 版本、支持架构、控制 API 连通状态和可执行文件来源。 |
| OpenClash 共存检查 | 检查 OpenClash 运行状态、端口冲突和资源占用风险。 |
| 监听地址 | 管理页面和管理 API 监听地址。 |
| 管理端口 | 管理页面和管理 API 端口。 |
| 测速核心端口 | Mihomo 控制 API 和本地测速代理入口端口；默认仅本机可访问。 |
| 开机启动 | 是否随 OpenWrt 启动。 |
| 数据目录 | 节点和测试数据保存位置。 |
| 最大测试并发 | 限制同时进行测试的节点数量。 |
| 日志级别 | 支持正常、详细和错误级别。 |
| 测试任务开关 | 分别控制连通性、Ping 和每日测速任务。 |
| 管理员账号 | 设置管理员登录账号。 |
| 管理员密码 | 设置或修改管理员登录密码。 |
| 打开管理后台 | 使用按钮在新页面打开 Bagualu 管理后台，不要求用户手工输入地址和端口。 |

页面必须提供明确的“启用/禁用”“启动”“停止”“重启”操作，并显示操作结果。禁用测速核心后，订阅管理和页面访问仍可用，但节点测试任务应进入暂停或失败状态并给出原因。

LuCI 页面还必须显示：Bagualu 版本、Mihomo 版本、OpenClash 是否运行、共存检查结果、端口冲突、最近错误和管理后台可访问状态。“打开管理后台”按钮仅在后台可访问时启用；不可访问时显示具体修复提示。

### 5.3 配置隔离与升级

- Bagualu 使用独立 UCI 配置命名空间，不复用 OpenClash 的 UCI section。
- 升级 Bagualu 时保留管理员设置、上游、节点、分组、API Key 和测试历史。
- 升级 Mihomo 前进行架构和版本校验，失败时保留当前可用版本。
- 服务配置变化需要明确提示“立即生效”或“需要重启”，不能静默重启 OpenClash 或其他服务。
- 管理员密码只保存安全摘要，LuCI 页面和日志不得回显密码。

## 6. 核心业务对象

| 对象 | 说明 |
| --- | --- |
| 上游订阅 | 代理节点的来源，包含订阅名称、地址、格式和刷新配置。 |
| 节点 | 从上游解析出的单个代理配置，包含协议、地址、端口和协议参数。 |
| 分组 | 一组节点的集合，可用于不同用途或不同 API 客户端。 |
| 测试结果 | 某个节点某次连通性、Ping 或下载测速的结果。 |
| API Key | 外部客户端访问指定分组资源的凭证。 |
| 后台任务 | 订阅刷新、节点测试和数据维护任务。 |
| 运行实例 | 当前测速核心服务为节点测试运行的核心实例，包含状态、节点、连接和流量信息。 |
| 流量报表 | 按时间、节点、分组和协议统计的测速流量和结果。 |
| 系统日志 | Bagualu 管理服务和测速核心服务的运行日志。 |

### 6.1 节点状态

节点需要至少支持以下状态：

- `active`：节点存在且可参与测试和分组资源输出。
- `unreachable`：最近连通性测试失败。
- `disabled`：管理员手动禁用。
- `expired`：节点已不在有效上游订阅中。
- `invalid`：节点配置解析失败或配置不完整。

节点状态和测试结果分开保存。Ping 成功不能直接将节点标记为可用，下载速度也不能替代连通性状态。

## 7. 节点测试需求

系统必须提供三类测试，三类测试独立调度、独立记录、独立展示。

### 7.1 协议级连通性测试

作用：验证节点能否按照自身协议建立连接并访问测试地址。

要求：

- 必须根据节点协议建立真实连接。
- 测试任务将节点配置和测试参数交给测速核心适配层，由测速核心服务完成协议连接。
- 不能只测试节点地址端口是否开放。
- 测试成功后记录成功状态、耗时和测试时间。
- 测试失败后记录失败原因和失败阶段。
- 需要记录测速核心服务返回的连接阶段、出口信息和请求结果。
- 连通性结果用于判断节点是否可以进入可用资源。

### 7.2 Ping 延迟测试

作用：定时观察节点地址的网络延迟。

要求：

- 定时执行，默认每分钟一次，可配置。
- 记录延迟、丢包和测试时间。
- 支持在 OpenWrt 环境下使用可用的 Ping 方式。
- Ping 结果只代表延迟表现，不代表代理协议一定可用。

### 7.3 实际下载测速

作用：测量通过节点代理连接后的真实下载速度。

要求：

- 必须按照节点协议连接成功后，再通过该连接实际下载测试文件。
- 测速程序负责生成测速参数，测速核心服务负责建立节点代理连接和承载下载请求。
- 默认每个节点每天测试一次。
- 测试文件地址、测试时间窗口、单次最大下载量和超时时间可配置。
- 记录实际下载速度、下载量、耗时、首字节时间、测试时间和失败原因。
- 速度必须根据实际下载字节数和有效下载耗时计算，不能使用代理节点声明的带宽值。
- 如果测速核心服务能够提供连接级流量统计，系统应优先使用核心统计作为测速依据，并同时保留应用层统计。
- 测速结果必须显示测试时使用的节点和协议。
- 测速结果必须显示“已由 Mihomo 验证”的状态和可追踪的内核证据摘要。
- 测速失败不能覆盖上一次成功的速度结果。
- 系统需要限制测速并发和总流量，避免影响 OpenWrt 正常网络使用。

测速任务完成后，测速核心适配层需要向 Bagualu 返回统一结果：任务状态、节点 ID、代理协议、测试地址、连接耗时、首字节耗时、下载字节数、有效下载耗时、下载速度、出口地址和失败原因。页面和 API 只使用统一结果，不直接依赖具体核心的返回格式。

### 7.4 测试策略

系统支持全局默认测试策略，也支持分组覆盖默认策略。策略至少包括：

- 是否启用该类测试。
- 执行周期。
- 超时时间。
- 测试地址。
- 并发数量。
- 节点纳入测试的条件。
- 节点进入资源输出的最低要求。

运行后台用于查看系统当前正在发生的事情，不承担基础配置功能。页面至少包含：

- Bagualu 管理服务状态和测速核心服务状态。
- 当前核心实例列表，包括实例状态、对应节点、启动时间和资源占用。
- 正在执行的订阅刷新、连通性测试、Ping 测试和下载测速任务。
- 当前连接数、活动测试数、实时下载速度和累计测试流量。

- 任务失败、核心异常和端口冲突提示。
- 跳转到节点详情、测试详情、流量报表和日志详情的操作入口。

首页和测试中心都需要提供进入运行后台的按钮。运行后台数据支持自动刷新或手动刷新。

### 8.5 流量报表

流量报表用于观察测速产生的流量和节点表现，至少支持：

- 按时间范围查看总测试流量、成功测试流量和失败测试流量。
- 按节点、分组、协议和上游筛选。

- 查看每日测速消耗的流量。
- 查看速度、延迟和连通性趋势。
- 导出报表数据。

报表中的测速流量与外部客户端通过资源 API 产生的访问流量分开统计。

### 8.6 日志管理

日志页面至少支持：

- 切换 Bagualu 管理服务日志和测速核心服务日志。

- 查看核心启动失败、节点连接失败、测速失败和配置错误。
- 下载或清理指定时间范围的日志。

日志页面不得展示完整 API Key、节点密码、UUID、私钥或订阅 URL 中的敏感 token。

### 8.7 管理后台视觉与交互规范

管理后台面向路由器管理员和代理节点运维人员，设计目标是安静、紧凑、清晰、长期查看不疲劳。它是操作后台，不使用营销式首页、巨大标题、装饰性渐变、悬浮卡片墙或无意义动画。

#### 8.7.1 视觉方向

视觉主题命名为“链路控制台”。页面以清晰的网络链路、实时状态和数据表格为主，核心识别元素是“链路证据条”：

```text
Bagualu [运行] -> Mihomo [已连接] -> HK-01 [VLESS] -> 测试目标 [200 OK]
                           连接 128 ms | 42.6 MB/s | 已验证
```

链路证据条出现在运行后台、节点详情和测试结果中，使用统一状态节点展示测试流量确实经过 Mihomo 和指定代理节点。

颜色令牌：

| 名称 | 色值 | 用途 |
| --- | --- | --- |
| Paper | `#F7F8FA` | 页面背景。 |
| Surface | `#FFFFFF` | 工具栏、表格和弹层背景。 |
| Graphite | `#20252B` | 主文字和导航。 |
| Signal Cyan | `#087EA4` | 当前选中、链接和实时链路。 |
| Healthy Green | `#16845B` | 可用、运行、测试成功。 |
| Warning Amber | `#B86A00` | 警告、资源压力和待处理。 |
| Fault Red | `#C43D3D` | 失败、停止和高风险。 |

状态不能只靠颜色表达，必须同时使用图标、文字或形状。深色模式不作为第一版强制要求，但色彩必须通过可访问性对比检查。

字体不依赖互联网字体服务：中文和普通界面使用 OpenWrt 客户端系统无衬线字体栈；端口、IP、流量、速度、时间和日志使用等宽字体栈。标题只用于建立信息层级，不使用超大展示字体。

#### 8.7.2 页面布局

桌面布局：

```text
+--------------+--------------------------------------------------+
| Bagualu      | 顶栏：服务状态 / 核心状态 / 运行后台 / 管理员     |
|              +--------------------------------------------------+
| 仪表盘       | 页面标题 + 筛选/主要操作                          |
| 上游订阅     +--------------------------------------------------+
| 节点         | 摘要指标或链路证据条                              |
| 分组         +--------------------------------------------------+
| 测试中心     | 主表格 / 报表 / 详情                              |
| 流量报表     |                                                  |
| 日志         +--------------------------------------------------+
| 设置         | 分页 / 状态栏                                    |
+--------------+--------------------------------------------------+
```

- 左侧导航固定宽度，按“资源、测试、系统”分区，不把每个功能做成首页卡片。
- 主工作区优先使用工具栏、表格、分栏详情和趋势图；卡片仅用于少量摘要指标或重复实体，圆角不超过 8px。
- 不允许卡片嵌套卡片，不把整个页面区块做成漂浮卡片。
- 表格列宽稳定，状态、延迟、速度和操作列对齐；数据变化不能造成布局跳动。
- 桌面端节点详情可使用右侧抽屉快速查看，完整历史通过独立详情页打开。
- 移动端导航折叠为抽屉，表格保留关键列并提供详情展开，按钮和文字不得重叠或截断。

#### 8.7.3 组件和操作

- 使用图标按钮表示刷新、启动、停止、重启、测速、复制、下载和查看日志；不熟悉的图标提供悬停说明。
- 二元设置使用开关；模式选择使用分段控件；多选使用复选框；端口和并发使用数字输入。
- 危险操作使用明确确认框，并写清影响对象；停止 Bagualu 不得暗示会停止 OpenClash。
- 每个异步操作显示排队、运行、成功、失败或取消状态，并提供任务详情入口。
- 空状态说明下一步可执行操作；错误状态给出错误原因和修复入口。
- 自动刷新页面需要显示刷新频率和最后更新时间，并允许暂停，避免实时数据造成持续闪烁。
- 图标和前端资源随安装包本地提供，不依赖公网 CDN。

#### 8.7.4 报表展示

- 仪表盘首先展示可用节点、异常节点、当前任务、实时测速流量和服务健康，不使用装饰性统计数字。
- 趋势图统一使用时间轴，支持查看原始数值和时间；成功率、延迟、速度和流量使用不同语义颜色。
- 节点排行同时显示协议、分组、最近测速时间和结果新鲜度，避免仅按一个速度数字误导排序。
- 所有报表都提供筛选条件摘要、空数据状态和数据更新时间。

#### 8.7.5 视觉验收

- 管理后台在 1440px、1024px、768px 和 390px 宽度下无文字遮挡、按钮溢出和不可操作区域。
- 键盘焦点清晰可见；表单标签、错误提示和状态图标具备可访问名称。
- 首页、节点列表、运行后台、节点详情、流量报表和系统设置保持统一导航、间距和状态语义。
- OpenClash 共存告警必须醒目但不阻断正常查看；只有确认存在启动风险时才禁止启动 Bagualu 核心。
- 页面截图评审必须覆盖正常、空数据、加载、失败、核心停止和 OpenClash 端口冲突状态。

## 10. 外部资源 API

外部客户端使用 API Key 访问资源 API。默认使用请求头鉴权：

```http
Authorization: Bearer <api-key>
```

### 10.1 资源接口

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| GET | `/resources` | 获取当前 API Key 绑定的默认分组资源。 |
| GET | `/resources/{group}` | 获取当前 API Key 有权访问的指定分组资源。 |
| GET | `/resources/{group}/nodes` | 以 JSON 返回分组节点。 |
| GET | `/resources/{group}/subscription` | 返回客户端可直接使用的订阅内容。 |
| GET | `/resources/{group}/stats` | 返回分组节点数量、可用数量和测试摘要。 |

资源接口支持以下参数：

- `format`：输出格式，例如 `json`、`base64`、`clash`。
- `protocol`：按代理协议筛选。
- `tag`：按标签筛选。
- `limit`：限制节点数量。
- `sort`：按稳定顺序、延迟或下载速度排序。
- `healthy_only`：是否只输出满足分组策略的节点。

资源输出默认只包含：节点存在、未被禁用、连通性满足策略且未过期的节点。是否要求最近测速成功由分组策略决定。

## 11. 数据关系

```text

API Key  N ---- 1 默认分组
```

- 节点为什么被排除出资源输出。

## 12. OpenWrt 页面与服务验收标准

### 12.1 服务验收

- 能在 OpenWrt 上安装并注册服务。
- 路由器重启后服务可以按配置自动启动。
- 可以通过 OpenWrt 服务命令启动、停止、重启和查看状态。
- 服务异常退出后可以自动恢复。
- Bagualu 管理服务和测速核心服务可以分别启用、禁用、启动、停止和重启。
- 管理员可以在页面修改管理员账号、密码、管理端口和测速核心服务端口。
- Bagualu 与 OpenClash 同时运行时，OpenClash 代理、DNS、规则、控制 API 和现有连接不受影响。
- Bagualu 启动、停止、升级和卸载前后，系统防火墙、路由、DNS 和 OpenClash 配置保持不变。
- 端口冲突只阻止 Bagualu 核心启动或触发自身端口重分配，不停止其他服务。
- 在不依赖 Docker 的情况下完成核心功能。
- 在有限内存和存储条件下限制测速并发及历史数据。

### 12.2 页面验收

- 管理员可以登录页面并看到首页统计。
- 可以创建上游并手动刷新，页面显示刷新结果。
- 可以查看节点列表、节点详情和节点来源。
- 可以创建分组并调整节点归属。
- 可以看到连通性、Ping、下载速度三类测试结果。
- 节点测试确实通过测速核心服务完成，而不是由页面或普通 HTTP 请求模拟。
- 页面可以查看测速核心服务运行状态、版本和测试任务占用情况。
- 页面可以查看协议能力矩阵，以及每种协议无法解析、加载或测试的具体原因。
- LuCI 页面可以运行共存检查，并通过按钮打开独立管理后台。
- 可以看到节点测试历史和失败原因。
- 可以通过按钮进入运行后台，查看当前核心实例、任务、连接数、实时速度和流量。
- 可以查看节点列表、流量报表、速度排行和历史趋势。
- 可以查看并筛选 Bagualu 服务和测速核心服务日志。
- 可以创建 API Key 并在页面中看到资源访问地址。
- 页面在 OpenWrt 常见桌面浏览器和移动浏览器上可用。

### 12.3 API 验收

- 管理 API 支持页面完成所有管理操作。
- 节点测试 API 确实按节点协议执行测试。
- 节点测试 API 能够驱动测速核心服务，并将核心连接和流量结果转换为统一测试结果。
- 停止 Mihomo 后发起节点测试，任务必须返回 `core_unavailable`，不得产生成功结果。
- 阻断 Mihomo 控制 API 后发起节点测试，任务必须返回 `core_api_unavailable`。
- 测试结果必须能够提供 Mihomo 实例、指定节点链路和流量差值证据。
- 测试请求无法确认经过指定节点时，必须返回 `core_route_unverified`，不得回退直连。
- 共存测试必须覆盖 OpenClash 正在运行时安装、启动、测速、停止、升级和卸载 Bagualu 的完整流程。
- 协议测试必须基于目标 Mihomo 版本的能力矩阵逐项执行配置加载和真实连通性测试。
- 系统能够通过运行后台接口展示测速核心服务返回的实时运行数据。
- 外部客户端使用 API Key 可以获取授权分组资源。
- 未授权客户端不能获取其他分组资源。
- 上游刷新失败不会清空上一次有效节点资源。

## 13. 代码架构与工程约束

本节是后续实现的强制约束。AI 大模型或开发人员编写代码时必须遵守；不得为了快速完成单个功能破坏模块边界、复制业务规则或将多个职责堆入同一文件。

### 13.1 架构原则

- 采用清晰的分层架构和依赖倒置，业务规则不直接依赖 HTTP 框架、数据库驱动、Mihomo 私有格式、OpenWrt 命令或 LuCI 实现。
- 单一职责：一个模块只承担一个明确变化原因，例如订阅解析、节点归组、测速编排、Mihomo 调用、任务存储分别维护。
- 高内聚、低耦合：同一业务能力放在同一模块，对外只暴露必要接口。
- 组合优于继承；只在存在多个真实实现或明确测试边界时增加接口和抽象。
- 复用业务能力，不复制业务规则。页面 API、定时任务和手动任务必须调用相同的应用服务。
- 禁止以 `utils`、`helpers`、`common` 等目录长期堆放无归属逻辑；通用代码必须有明确领域或基础设施归属。
- 架构允许未来替换存储、Web 框架和测速核心，但不为没有明确需求的场景提前设计复杂插件系统。

### 13.2 分层与依赖方向

```text
入口层（HTTP / CLI / 定时器 / LuCI RPC）
                    |
                    v
应用层（用例编排 / 事务 / 权限 / 任务协调）
                    |
                    v
领域层（实体 / 值对象 / 规则 / 接口契约）
                    ^
                    |
基础设施层（数据库 / Mihomo / OpenWrt / 日志 / 文件系统）
```

依赖规则：

- 入口层可以依赖应用层，不得绕过应用层直接操作数据库或 Mihomo。
- 应用层可以依赖领域层定义的接口，不得依赖具体数据库表、Mihomo YAML 字段或 shell 命令细节。
- 领域层不得依赖入口层、基础设施层、Web 框架、ORM 或操作系统。
- 基础设施层实现领域层或应用层定义的端口接口，负责所有外部系统细节。
- 前端只能通过版本化 API 使用后端能力，不直接读取数据库文件、UCI 文件或 Mihomo 配置。
- LuCI 页面只调用受控 RPC/HTTP 接口，不直接拼接 shell 命令执行服务操作。

### 13.3 后端模块边界

后端至少按以下业务模块组织：

| 模块 | 职责 | 禁止承担 |
| --- | --- | --- |
| `auth` | 管理员认证、会话、密码修改。 | 节点或系统服务管理。 |
| `upstream` | 上游 CRUD、刷新编排、刷新记录。 | 直接执行节点测速。 |
| `subscription` | 格式识别、订阅解析、节点标准化。 | 数据持久化和 HTTP 响应。 |
| `node` | 节点查询、状态、来源和管理属性。 | Mihomo 进程控制。 |
| `group` | 分组、节点归属和输出策略。 | API Key 鉴权实现。 |
| `measurement` | 连通性、Ping、测速任务编排和结果计算。 | Mihomo 私有 API 调用。 |
| `core` | 测速核心抽象、能力矩阵和内核证据模型。 | 页面或数据库框架代码。 |
| `mihomo` | 配置生成、进程管理、控制 API 和代理端口适配。 | 业务分组和资源授权规则。 |
| `openwrt` | procd/UCI/ubus/LuCI 集成、共存检测和系统状态。 | 节点解析和测速计算。 |
| `resource` | API Key 授权、分组资源筛选和订阅输出。 | 修改上游或节点。 |
| `job` | 调度、并发限制、取消、重试和任务状态。 | 具体业务规则。 |
| `report` | 统计查询、趋势和导出。 | 修改原始测试结果。 |
| `audit` | 操作审计和敏感信息脱敏。 | 执行业务操作。 |

跨模块调用通过公开应用服务或明确接口完成，不得直接访问其他模块内部 repository、未导出类型或私有数据结构。

### 13.4 前端模块边界

- 页面按业务路由拆分：仪表盘、上游、节点、分组、测试、运行后台、报表、日志和设置。
- 页面组件负责组合和交互，不在组件内实现 API 权限、测速规则或数据聚合算法。
- API 客户端、查询状态、表单校验、图表数据转换和展示组件分别组织。
- 可复用组件必须来自至少两个真实使用场景；只用于单一页面的组件保留在页面模块内部。
- 全局状态只保存跨路由且确有共享需求的数据，例如管理员会话和系统运行摘要；筛选、分页和弹窗状态保留在页面内。
- 状态文案、状态颜色、时间、速度和流量格式化使用集中定义，避免各页面出现不同语义。
- LuCI 设置页与独立管理后台可以使用不同构建入口，但共享 API 契约和状态定义，不复制后端业务逻辑。

### 13.5 参考项目结构

实际语言和框架确定后可以调整目录名称，但职责和依赖方向必须保持：

```text
bagualu/
  cmd/                  # API 服务、任务进程、维护命令入口
  internal/
    domain/             # 领域模型、规则、错误和端口接口
    application/        # 业务用例与编排
    modules/            # upstream/node/group/measurement/resource 等模块
    infrastructure/
      persistence/      # 数据存储实现
      mihomo/           # Mihomo 适配器
      openwrt/          # procd/UCI/ubus 集成
      logging/          # 日志与审计实现
    transport/
      http/             # 路由、请求响应 DTO、中间件
      cli/              # 命令行入口适配
  web/
    admin/              # 独立管理后台
    luci/               # OpenWrt LuCI 设置入口
    shared/             # API 契约和真正共享的前端能力
  packaging/openwrt/    # OpenWrt 包、init、UCI 和安装升级脚本
  tests/                # 跨模块集成、系统和验收测试
  docs/                 # SDD、API 和运维文档
```

### 13.6 文件规模与代码拆分

- 手写源码单文件硬性上限为 **1000 行**，目标控制在 **500 行以内**。
- 文件达到 500 行时，代码评审必须检查是否存在职责过多；达到 800 行时必须制定拆分方案；不得合入超过 1000 行的手写源码。
- 自动生成代码、协议生成文件、数据库迁移和第三方代码可以超过 1000 行，但必须放在明确的 `generated`、`migrations` 或 `vendor` 边界中，禁止手工混入业务逻辑。
- 单个函数应完成一个任务。出现多级流程、多个外部依赖或大量分支时，拆成可命名、可测试的步骤。
- 一个文件不同时包含 HTTP 路由、业务规则、数据库查询和系统命令调用。
- 不通过压缩格式、超长行或把代码塞入大字符串规避文件行数约束。
- 拆分依据是职责和变化原因，不以机械方式将一个大文件切成无语义的 `part1`、`part2`。

### 13.7 接口、模型与错误

- HTTP 请求/响应 DTO、领域模型、数据库模型和 Mihomo 配置模型分离，转换在模块边界完成。
- API 契约集中维护并版本化；前后端不得各自手写一套含义不同的状态枚举。
- 接口应小而明确，由使用方定义；禁止创建包含大量无关方法的万能 Service 或 Repository。
- 领域错误使用稳定错误码，例如 `core_unavailable`、`node_load_failed`，入口层负责转换为 HTTP 状态和用户可读信息。
- 外部错误必须保留原因链和上下文，但日志不得泄露管理员密码、API Key 或节点敏感参数。
- 时间统一保存为 UTC，API 使用标准时间格式，页面按用户时区展示。
- 速度、流量、延迟和比例使用明确单位，禁止以无单位数字在模块间传递。

### 13.8 Mihomo 与 OpenWrt 隔离

- `measurement` 模块只依赖核心接口，不允许直接调用 Mihomo HTTP API 或执行 Mihomo 命令。
- 所有 Mihomo 私有配置、API 路径和进程信号集中在 `infrastructure/mihomo`。
- 所有 UCI、ubus、procd、文件路径、进程查询和端口检测集中在 `infrastructure/openwrt`。
- Mihomo 适配器和 OpenWrt 适配器都必须可由测试替身替换，业务测试不得要求真实路由器或真实核心。
- 真实 Mihomo/OpenWrt 测试放入独立集成测试和系统验收测试，不与快速单元测试混合。
- 共存检查独立于修复动作；检测模块只能报告风险，只有 Bagualu 自身配置允许由管理用例修改。

### 13.9 测试与质量门禁

- 领域规则和应用服务必须有单元测试，覆盖成功、失败、超时、取消和重复执行。
- Mihomo 适配器使用契约测试，验证配置生成、API 响应转换、错误映射和进程回收。
- HTTP API 使用集成测试验证认证、权限、参数、错误码和响应模型。
- 前端关键页面覆盖组件测试；上游添加、节点测速、分组授权和打开运行后台覆盖端到端测试。
- OpenClash 共存、Mihomo 真实链路、安装升级和卸载使用 OpenWrt 环境验收测试。
- 每次合入必须通过格式化、静态检查、单元测试、架构依赖检查、单文件行数检查和敏感信息扫描。
- 测试不得依赖执行顺序、固定端口、公网稳定性或开发者机器上的 OpenClash 配置。
- 修复缺陷必须增加能够复现该缺陷的测试，除非评审记录明确说明无法自动化的原因。

### 13.10 可读性与文档

- 命名使用业务语言，保持上游、节点、分组、测试任务、核心实例等术语在代码、API 和页面中一致。
- 避免无意义缩写、单字母变量和含糊名称，例如 `data`、`manager`、`handleAll`。
- 注释解释约束、原因和非显然取舍，不复述代码行为；复杂链路在入口处提供简短说明。
- 对外模块、公共接口、错误码、配置项和 API 必须有文档。
- 重要架构决策使用 ADR 记录，包括技术栈、存储、Mihomo 调用模式和 OpenWrt 打包方式。
- SDD 是需求和架构基线；实现与 SDD 不一致时，必须先更新文档并评审，不允许代码静默偏离。

### 13.11 架构验收标准

- 从 HTTP 路由可以清晰追踪到应用用例、领域接口和基础设施实现，没有跨层捷径。
- 手动触发测试和定时测试复用同一测量应用服务，结果计算只有一份实现。
- 更换 Mihomo 测试替身不需要修改测量业务规则；更换存储实现不需要修改 HTTP 路由。
- LuCI 和独立管理后台通过相同后端契约完成服务控制，不包含两套启停逻辑。
- 仓库不存在超过 1000 行的手写源码文件；超过 500 行的文件有明确保留理由或拆分记录。
- 模块依赖检查没有循环依赖，领域层不依赖基础设施层。
- 新增协议只需要扩展订阅解析/统一节点模型和 Mihomo 配置转换，不需要修改分组、报表和 API Key 模块。
- 新增页面不要求复制 API 客户端、状态颜色、单位格式化或权限逻辑。
